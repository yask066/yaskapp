# PostgreSQL и MinIO: backup и пробное восстановление

Эта схема делает согласованную зашифрованную копию БД, полного тома MinIO и файлов
развёртывания. Сейчас репозиторий находится на диске VPS: это не защита от потери
диска или всего VPS. Для такой защиты нужен отдельный удалённый репозиторий.

## Установка

Для Linux Docker host, root, checkout `/opt/yaskapp`, project `yaskapp-staging`.
Нужны Docker, Python 3, systemd и restic >= 0.14. Установщик устанавливает отсутствующий
restic через apt, сохраняет существующие пароль/репозиторий и не печатает реквизиты.

```sh
bash infra/backup/install.sh
```

Установщик выполняет preflight и тестирует backup/restore на отдельном Docker-проекте
с образами сервера. Затем он устанавливает units, запускает первый рабочий backup и
проверку восстановления. **Первый рабочий backup кратко приостановит API и workers.**
Timers включаются после успешных backup и restore.

Пароль: `/etc/yaskapp/backup/restic-password`, root-only, вне Git. Сохраните его
отдельно от VPS; не вставляйте в чат. Сам пароль не входит в snapshot.
Конфигурация: `/etc/yaskapp/backup/config.json`, root-only.
Репозиторий по умолчанию: `/var/backups/yaskapp/restic`; рабочая директория:
`/var/lib/yaskapp-backup`. Права этих директорий — 0700.

## Расписание и согласованность

- Backup ежедневно в **04:00 Europe/Minsk**. Пропущенный ночной запуск не выполняется
  автоматически посреди дня; после установки есть первая проверенная копия.
- Проверка восстановления по воскресеньям в **05:00 Europe/Minsk**; пропущенная
  проверка догоняется после включения сервера и не останавливает приложение.
- Retention: снимки за 30 дней и последний успешный снимок на случай длительного
  сбоя расписания. Удаление старых данных запускается только после успешной новой
  копии и проверки репозитория.

Backup берёт общую блокировку, проверяет место/контейнеры, приостанавливает таймер
очистки аватаров и ранее работавшие API/workers. Инспектор читает таблицы, sequence
и все текущие S3-объекты; сохраняются контрольные значения и SHA256 медиа. Создаётся
pg_dump, затем останавливается MinIO и restic копирует его холодный том вместе с
dump и файлами env/Compose/Caddy/Firebase. Перед паузой экспортируется точный образ
MinIO. Он входит в зашифрованный snapshot и позволяет загрузить образ при отсутствии
его локальной копии. Внутренние метаданные и версии объектов MinIO входят в холодный
том. S3-проверка сравнивает текущие объекты приложения.

После снимка возвращаются ранее работавшие контейнеры и таймеры. Работа со снимком
ограничена пятью минутами, после чего начинается восстановление сервисов.
Ошибка или прерывание также запускает восстановление сервисов.
Systemd ExecStopPost восстанавливает сервисы по защищённому marker даже после
остановки основного процесса. PostgreSQL при backup не останавливается.
Не запускайте вручную другие изменяющие данные задания во время maintenance.

Секреты файлов развёртывания и MinIO находятся внутри шифрованного snapshot.
Промежуточная директория доступна только root. В логах есть только размеры,
статусы, snapshot ID и безопасные диагностические сообщения.

## Проверка восстановления

```sh
systemctl start yaskapp-backup-verify.service
python3 /usr/local/libexec/yaskapp-backup/staging_backup.py status
systemctl list-timers --all yaskapp-backup.timer yaskapp-backup-verify.timer
journalctl -u yaskapp-backup.service -u yaskapp-backup-verify.service -n 80 --no-pager
```

Проверка читает весь репозиторий, извлекает последний успешный snapshot с проверкой файлов,
восстанавливает БД в новый PostgreSQL-контейнер и холодный том в новый MinIO-контейнер.
Для PostgreSQL и инспектора нужен доступ к образам, указанным в snapshot. Если
локальный образ MinIO отсутствует, проверка загружает его из snapshot. Резервная
копия предназначена для восстановления данных и файлов развёртывания приложения.

Сеть Docker — internal, внешних портов нет. Рабочие тома и endpoints не служат
целями восстановления, API и workers к тестовой БД не подключаются. Сравниваются
хеши/число строк всех пользовательских таблиц, состояния sequence и SHA256 всех
текущих медиаобъектов. Push из восстановленного окружения не отправляется.

Временные контейнеры/тома/сеть имеют случайные имена и ownership label. Очистка
проверяет их принадлежность и не удаляет другие ресурсы. После прерывания служба
выполняет `cleanup`; marker позволяет повторить очистку безопасно.

## Ошибки и ручное восстановление

Успех: `last-backup.json` и `last-verify.json` со `status=success` и нужным snapshot.
Ошибка: ненулевой статус systemd и `last-failure.json` с временем/операцией. Последняя
ошибка сохраняется как история даже после нового успешного запуска: сравнивайте
времена. Внешний канал оповещений пока не настроен.

```sh
python3 /usr/local/libexec/yaskapp-backup/staging_backup.py resume
python3 /usr/local/libexec/yaskapp-backup/staging_backup.py cleanup
```

Для переключения рабочего стенда на восстановленные данные требуется отдельное
окно обслуживания и план: учесть удаления аккаунтов после даты снимка, совместимость
образов/миграций и проверить приложения до открытия трафика. Автоматическая drill
этого переключения не делает. Удаление приложения после даты снимка не отменяется
за счёт запуска восстановленных копий в рабочем окружении.

Для запуска автоматических тестов самого coordinator:

```sh
python3 -m unittest discover -s infra/backup -p 'test_*.py'
```

POSIX проверки прав должны выполняться на Linux; под Windows они пропускаются,
а защита permissions в тестах orchestration заменяется только на время теста.
