# PRD: Поиск опросов и пользователей

**Статус:** Draft for review  
**Дата:** 30 августа 2026 года  
**Продукт:** Yaskapp mobile  
**Владелец:** Product / Engineering  

## 1. Краткое описание

Yaskapp нужен единый поиск, чтобы авторизованный пользователь мог быстро находить опубликованные опросы и публичные профили. В MVP поиск запускается из иконки Search в шапке Feed и работает по тексту опроса, username и display name.

Результаты показываются единым списком с переключателем типа: «Все», «Опросы», «Пользователи». Поиск выполняется сервером через единый API-контракт и использует PostgreSQL без добавления отдельного поискового сервиса.

## 2. Проблема и цель

Сейчас в приложении нет пользовательского поиска, а иконка поиска в Feed не выполняет действие. Пользователь может открыть профиль из существующего контента, но не может найти человека или опрос напрямую.

**Цель MVP:** дать пользователю предсказуемый способ найти нужный опрос или профиль по короткому текстовому запросу.

**Не является целью MVP:** построить рекомендательную ленту, тематический discovery или универсальный поиск по всему контенту Yaskapp.

## 3. Пользователи и сценарии

### Основные пользователи

- пользователь, который помнит текст или часть текста опроса;
- пользователь, который знает username или имя другого пользователя;
- пользователь, который хочет открыть найденный профиль и подписаться на него;
- пользователь, который хочет открыть опрос, проголосовать, поставить лайк или открыть комментарии.

### Основной сценарий

`Feed → Search → ввод запроса → выбор типа/сортировки → просмотр результата → открытие опроса или профиля`

### Дополнительные сценарии

- пользователь меняет тип результата, сохраняя текущий запрос;
- пользователь меняет сортировку и получает первую страницу заново;
- пользователь доскролливает до конца и загружает следующую страницу;
- пользователь повторяет запрос после сетевой ошибки;
- пользователь очищает запрос и возвращается в initial state.

## 4. Объём MVP

### Входит в MVP

- отдельный Flutter Search Screen;
- запуск экрана из иконки Search в Feed;
- поиск опросов по тексту вопроса;
- поиск пользователей по username и display name;
- переключатель «Все» / «Опросы» / «Пользователи»;
- сортировка по релевантности, свежести и популярности там, где она применима;
- debounce ввода 300–500 мс;
- серверная cursor-пагинация;
- состояния initial, loading, results, empty, error, pagination loading и offline/timeout;
- переход к публичному профилю;
- переход к найденному опросу с сохранением доступных действий;
- rate limit, проверка авторизации и проверка видимости данных;
- backend- и Flutter-тесты;
- аналитические события без передачи полного текста запроса.

### Не входит в MVP

- хэштеги;
- категории и темы;
- поиск по комментариям;
- фильтры по стране;
- фильтры по дате и статусу;
- фильтр «есть аватар»;
- история запросов и сохранённые поиски;
- персональные рекомендации;
- внешний поисковый движок;
- обязательный Redis-кэш результатов.

## 5. UX и функциональные требования

### 5.1. Search Screen

Экран содержит:

- строку поиска с автоматическим фокусом;
- кнопку очистки, отображаемую при непустом запросе;
- переключатель типа результата;
- контрол сортировки;
- прокручиваемый список результатов.

Клавиатура должна запускать поиск по submit/action Search. Ввод запроса должен сохраняться при переключении типа или сортировки. При повторном открытии экрана поиск начинается с пустого запроса.

### 5.2. Типы результатов

Для опроса используются существующие данные `PollSummary` и существующий компонент `PollCard` в компактном режиме. Пользователь может открыть опрос и использовать разрешённые действия приложения.

Для пользователя отображаются:

- аватар, если он доступен;
- display name;
- username;
- краткая публичная статистика, если она уже присутствует в модели публичного профиля.

Нажатие на пользователя открывает существующий `PublicProfileScreen`.

### 5.3. Сортировка

- `relevance` — доступна для опросов и пользователей;
- `newest` — доступна для опросов; для пользователей может быть скрыта в UI, если дата регистрации не является частью публичной модели;
- `popular` — доступна для опросов и пользователей, если необходимые счётчики доступны в текущих моделях.

Если сортировка не применима к типу результата, клиент не показывает её, а сервер отклоняет неподдерживаемое сочетание с `400`.

### 5.4. Состояния

- **Initial:** подсказка, что можно найти опрос или пользователя.
- **Loading:** skeleton или индикатор загрузки.
- **Results:** список результатов и доступные контролы.
- **Empty:** «Ничего не найдено» и предложение изменить запрос.
- **Error:** понятное сообщение и повторная попытка; введённый запрос сохраняется.
- **Pagination loading:** индикатор внизу списка.
- **Offline/timeout:** сообщение о недоступности сети без потери введённого запроса.

При запросе короче 2 символов поиск не отправляется; клиент показывает подсказку о минимальной длине запроса. Максимальная длина — 100 символов.

## 6. API-контракт

```http
GET /search?q=<query>&type=all|polls|users&sort=relevance|newest|popular&cursor=<cursor>&limit=20
Authorization: Bearer <accessToken>
```

### Параметры

- `q` — trim-значение длиной от 2 до 100 символов;
- `type` — `all`, `polls` или `users`; по умолчанию `all`;
- `sort` — `relevance`, `newest` или `popular`; по умолчанию `relevance`;
- `cursor` — opaque cursor для следующей страницы;
- `limit` — от 1 до 50, по умолчанию 20.

Неизвестные параметры и неподдерживаемые сочетания отклоняются с `400`.

### Ответ

```json
{
  "items": [
    {
      "type": "poll",
      "poll": { "...": "PollSummary" },
      "score": 0.92
    },
    {
      "type": "user",
      "user": { "...": "PublicProfile" },
      "score": 0.87
    }
  ],
  "nextCursor": "opaque-cursor-or-null"
}
```

`score` используется для отладки и аналитики, но не является обязательным для отображения клиентом. Для ответа с `type=polls` или `type=users` элементы содержат только соответствующий тип. Для `type=all` сервер возвращает смешанный список в едином порядке.

### Ошибки

- `400` — неверные параметры, короткий запрос или неподдерживаемая сортировка;
- `401` — отсутствует или недействителен access token;
- `429` — превышен rate limit;
- `500` — внутренняя ошибка поиска.

## 7. Поиск и ранжирование

PostgreSQL остаётся источником истины. В MVP не добавляется Elasticsearch, Meilisearch, Typesense или другая поисковая инфраструктура.

### Поля поиска

- опросы: текст вопроса;
- пользователи: username и display name.

Правила:

- регистр и лишние пробелы игнорируются;
- точное совпадение выше частичного;
- `relevance` использует PostgreSQL full-text search для текста опросов и trigram-поиск для username/display name;
- `newest` сортирует по `created_at`;
- `popular` использует стабильный popularity score на основе доступных голосов, лайков и комментариев для опросов и публичных счётчиков для пользователей;
- при одинаковом score применяются `created_at`, затем ID для стабильной cursor-пагинации;
- deleted, blocked и недоступные пользователю сущности не попадают в выдачу.

Точные выражения popularity score и веса релевантности должны быть зафиксированы в техническом плане до реализации и покрыты тестами. Они не меняют пользовательский контракт API.

## 8. Архитектура и границы изменений

### Mobile

Добавить search feature по существующему feature-подходу Flutter. Экран использует существующие клиенты и модели там, где это возможно, и отдельный `SearchApiClient` для нового endpoint.

Ожидаемые зоны изменений:

- обработчик иконки Search в `FeedScreen`;
- новый Search Screen и его состояние;
- клиент поиска, DTO и модели результатов;
- компактное отображение `PollCard` и переиспользование `PublicProfileScreen`;
- тесты Search Screen и API client.

### API

Добавить отдельный search module или эквивалентную изолированную границу в `services/api`, включая:

- route с auth и rate limit;
- validation query parameters;
- service с нормализацией запроса, поиском и курсорной пагинацией;
- repository queries и PostgreSQL indexes;
- API tests.

PostgreSQL — источник истины. Redis может использоваться позднее для кэширования горячих запросов, но не является частью критериев готовности MVP.

## 9. Аналитика и приватность

События:

- `search_opened`;
- `search_submitted`;
- `search_filter_changed`;
- `search_result_clicked`;
- `search_empty`;
- `search_error`.

События могут передавать длину запроса, выбранный тип, сортировку, тип результата и позицию результата. Полный текст пользовательского запроса не передаётся в аналитику.

## 10. Метрики успеха

### Технические

- не менее 90% поисковых запросов отвечают за ≤500 мс на staging-данных;
- cursor-пагинация не создаёт дублей и пропусков в пределах стабильного набора данных;
- ошибки API корректно отображаются и повторяются;
- недоступные, удалённые и заблокированные данные не раскрываются.

### Продуктовые

После запуска отслеживаются:

- доля поисков, завершившихся открытием результата;
- доля пустых поисков;
- распределение запросов по типам и сортировкам;
- повторные поиски после пустого результата;
- latency и error rate endpoint’а.

Целевые продуктовые значения будут определены после получения baseline за первый период использования, поскольку текущей поисковой воронки нет.

## 11. Критерии готовности

Фича готова к staging-проверке, если:

- иконка Search в Feed открывает Search Screen;
- поиск опросов и пользователей работает через единый endpoint;
- доступны переключатель типа и применимые сортировки;
- реализованы debounce, submit, очистка и cursor-пагинация;
- существуют и проверены все перечисленные UI-состояния;
- найденный опрос открывается с доступными действиями, профиль — через `PublicProfileScreen`;
- есть backend-валидация, auth, rate limit и visibility checks;
- добавлены PostgreSQL indexes и миграция без нарушения migration guard;
- backend- и Flutter-тесты проходят;
- аналитические события не содержат полный текст запроса;
- API и поведение экрана документированы.

## 12. Риски и меры

| Риск | Мера |
| --- | --- |
| PostgreSQL-поиск станет медленным при росте данных | Добавить индексы, измерить latency на staging, вынести поисковый движок в отдельный follow-up при необходимости |
| Смешанная выдача будет непредсказуемой | Зафиксировать единое ранжирование и стабильный tie-breaker в тестах |
| Cursor-пагинация ломается при изменении популярности | Использовать составной cursor по score/created_at/ID и документировать консистентность страницы |
| В выдачу попадут недоступные сущности | Выполнять visibility predicates на уровне repository query и покрыть integration tests |
| Частые вводы создают нагрузку | Debounce на клиенте, rate limit на API, ограничение длины запроса и page size |

## 13. Follow-up после MVP

- страны, категории, статусы и даты;
- хэштеги и поиск по комментариям;
- история и сохранённые поиски;
- подсказки и autocomplete;
- персональное ранжирование;
- dedicated search engine при подтверждённой нагрузке;
- модерационные инструменты для контроля поисковой выдачи.
