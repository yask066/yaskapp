# Личная блокировка: карта проверок API

Карта составлена 29 октября 2026. Это требования к будущим проверкам,
а не подтверждение готовой защиты. [Правила и приёмка](../prd-user-blocking.md),
[задачи UB](../superpowers/plans/2026-10-29-user-blocking-task-breakdown.md).

Во всех строках A и B блокируют друг друга хотя бы в одном направлении;
C — независимый пользователь для проверки обычного поведения.
Для каждого маршрута нужны отрицательный сценарий A/B и разрешённый сценарий C.
Назначение UB-08–UB-19 сохраняется для интеграционных тестов соответствующих модулей.

## HTTP

| Метод и путь | Задача | Что проверить |
| --- | --- | --- |
| `GET /users` | UB-10 | B отсутствует у A; фильтрация до limit/cursor, доступный C заполняет страницу. |
| `GET /users/:userId` | UB-08 | Для A↔B общий 404; доступ C определяется обычными правилами. |
| `GET /users/:userId/followers` | UB-08 | A не видит B в списке C; остальные записи доступны с пагинацией. |
| `GET /profiles/me/following` | UB-08 | После блока нет взаимных подписок A/B; чужие связи и счётчики не изменены. |
| `POST /users/:userId/follow` | UB-08 | Проверка сериализована с block; новые связь и счётчик не создаются. |
| `DELETE /users/:userId/follow` | UB-08 | Повтор идемпотентен; unblock не восстанавливает подписку и не меняет чужие связи. |
| `GET /profiles/me/polls` | UB-08 | Собственные опросы доступны; загрузка не раскрывает скрытые данные другого автора. |
| `GET /users/:userId/polls` | UB-08 (маршрут); UB-09 (загрузка опроса) | Список B для A возвращает 404; старые ID не обходят актуальную проверку опроса. |
| `POST /polls` | UB-09 | Создание своего опроса работает и не затрагивает скрытый контент другого аккаунта. |
| `DELETE /polls/:pollId` | UB-09 | Автор может удалить свой опрос; чужое удаление по-прежнему запрещено. |
| `GET /polls/:pollId` | UB-09 | Для A↔B общий 404 при любой visibility; C доступен по обычным правилам. |
| `GET /polls` | UB-11 (пагинация); UB-09 (загрузка опроса) | Старые cursor/snapshot не возвращают B; доступный C достижим без зацикливания. |
| `GET /polls/subscriptions` | UB-11 (пагинация); UB-09 (загрузка опроса) | Используются текущие follows и blocks; B скрыт, доступный C достижим. |
| `POST /polls/:pollId/votes` | UB-09 | Нельзя голосовать в скрытом опросе B; старые голоса и агрегаты сохраняются. |
| `PUT /polls/:pollId/votes` | UB-09 | Нельзя обойти политику через маршрут смены голоса; старые голоса и агрегаты неизменны. |
| `DELETE /polls/:pollId/votes` | UB-09 | Отмена в скрытом опросе возвращает 404; разрешённая отмена у C работает. |
| `POST /polls/:pollId/likes` | UB-09 | В скрытом опросе B лайк и счётчик не создаются. |
| `DELETE /polls/:pollId/likes` | UB-09 | Нельзя прочитать или изменить скрытый опрос B через отмену лайка. |
| `GET /polls/:pollId/comments` | UB-12 | Нет автора/body/preview B; заглушка по capability сохраняет доступные ответы A/C и следующие страницы. |
| `GET /polls/:pollId/comments/:commentId` | UB-12 | Чтение по ID и preview родителя не раскрывают автора/body скрытого комментария B. |
| `GET /polls/:pollId/comments/:commentId/replies` | UB-12 | Ответы B скрыты; доступные A/C читаются и на второй странице без раскрытия родителя. |
| `POST /polls/:pollId/comments` | UB-13 | В транзакции проверяются авторы опроса и родителя. Ответ B запрещён; отдельное обсуждение с C разрешено. |
| `DELETE /polls/:pollId/comments/:commentId` | UB-13 | Удаление своего комментария возвращает 204 без загрузки скрытого опроса; чужое запрещено. |
| `POST /polls/:pollId/comments/:commentId/likes` | UB-13 | Проверяются авторы опроса и комментария: лайк B запрещён, доступного C разрешён. |
| `DELETE /polls/:pollId/comments/:commentId/likes` | UB-13 | Отмена не раскрывает и не меняет скрытый комментарий B; разрешённое действие у C работает. |
| `GET /search` | UB-10 | Профили и опросы B исключены до limit/cursor; C достижим после скрытых кандидатов. |
| `GET /media/polls/:pollId` | UB-14 | Проверка до body и 304; guest-кэш и переход к авторизованному A не раскрывают изображение B. |
| `GET /media/avatars/:userId` | Публичный доступ | Публичный аватар остаётся публичным: это утверждённая граница защиты. |
| `GET /notifications` | UB-16 | Учитываются actor, владельцы целей и устойчивое suppression; история B скрыта, C сохранён. |
| `GET /notifications/unread-count` | UB-16 | Unread исключает старые события B с commit блока и после unblock. |
| `POST /notifications/:id/read` | UB-16 | Адресный read не обходит suppression; доступное уведомление C можно прочитать. |
| `POST /notifications/read-all` | UB-16 | Read-all меняет только доступные записи пользователя; скрытая история не возвращается. |
| `POST /reports` | UB-15 | Жалоба на известный ID B доступна после блока; ответ не раскрывает скрытый контент. |
| `GET /reports/mine` | UB-15 | Свой статус жалобы доступен; скрытый контент B не добавляется в ответ. |
| `GET /moderation/cases/:caseId` | UB-15 | Модератор, лично заблокированный B, читает дело по полномочиям; обычный пользователь — нет. |
| `POST /auth/account-deletion/verification` | UB-15 | Проверка удаления доступна независимо от личного блока; ответ не содержит лишних данных отношений. |
| `GET /auth/account-deletion/status` | UB-15 | Статус приватен для удаляющего аккаунта; A не получает статус B, включая повтор username. |
| `DELETE /auth/me` | UB-15 | Удаление очищает отношения; новый UUID с тем же username ничего не наследует. |
| `GET /realtime` (WebSocket upgrade) | UB-18 | Каждый получатель проверяется отдельно: A не получает полный payload B; безопасные агрегаты C допустимы. |
| `POST /profiles/me/avatar`, `DELETE /profiles/me/avatar`, `PATCH /profiles/me` | Контроль своего профиля | Свои профиль и аватар можно менять; блок другого человека на них не влияет. |
| `POST /notification-devices`, `DELETE /notification-devices`, `GET /notification-preferences`, `PATCH /notification-preferences` | UB-17 контроль | Блок не удаляет свои устройства/настройки и не мешает их изменению. |

Управление блоками — `PUT/DELETE/GET /users/:userId/block`,
`GET /profiles/me/blocks` и `GET /profiles/me/visibility` — относится к UB-07.
В текущем API нет `GET /notifications/:id`: адресная проверка идёт через
`POST /notifications/:id/read`. Если GET появится, он должен соблюдать то же suppression.

## Внутренние пути

| Путь | Задача | Что проверить |
| --- | --- | --- |
| `hydratePolls`, загрузка опросов профиля и поиска | UB-08–UB-11 | Старый ID не возвращает body B; доступный C за ним не теряется. |
| Корень, preview родителя, поиск ответа по ID | UB-12 | Нет автора/body/excerpt B; доступные A/C достижимы после первой страницы. |
| Поиск родителя при создании ответа | UB-13 | Ответ B запрещён в границе мутации, даже в опросе C и по известному ID. |
| Владелец изображения, ETag/conditional GET | UB-14 | A не получает изображение B или 304 после блока. |
| Создание уведомления, actor/owner, inbox/read/unread | UB-16 | История B подавлена с commit; контрольное уведомление C остаётся. |
| Claim/retry и отправка push провайдеру | UB-17 | При авторизации после commit блока send не вызывается; job окончательно подавлена. |
| Broadcast опросов/уведомлений и Redis bus | UB-18 | Нет скрытого payload B; ошибка проверки запрещает доставку; ревизия не раскрывает вторую сторону. |
| Outbox claim/publish/ack и восстановление | UB-19 | Повторы и иной порядок событий не откатывают ревизию и не возвращают историю. |
| Завершение удаления аккаунта | UB-15 | Отношения удаляются; повтор username с новым UUID их не наследует. |

Авторизация, сессии и служебные маршруты модерации сохраняют обычные проверки
владельца и полномочий. Роль модератора не обходит личный блок в обычном
пользовательском API.
