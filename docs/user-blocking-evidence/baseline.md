## Reproduction setup

Use a disposable PostgreSQL database, never a shared or production database. Point `DATABASE_URL` at that database and apply the repository migrations:

```sh
npm run db:migrate
```

The fixture itself uses a deterministic seed and writes only rows whose IDs are derived from that seed. After a run, call `cleanupUserBlockingFixtures`; it deletes only those explicit IDs and account-owned follow edges. The no-block baseline seed is:

```text
ub03-baseline-2026-10-29
```

It represents the unblocked state. The four block states in the fixture are policy scenarios only; UB-04 has not added a `user_blocks` table, so the seeder does not create personal-block rows.

## Dataset

Generated by `services/api/src/modules/user-blocks/user-blocks.fixtures.ts` with fixed timestamps and seed-namespaced UUIDs:

- 7 accounts: A, B, C, moderator, deleted/unavailable account, globally blocked account, and a current account whose username was previously used by a different UUID.
- 2 reciprocal follow edges, A↔B; profile follow counters are derived from those edges.
- 7 polls: A and B each have public/followers/private polls; C has a public poll used for the shared discussion.
- 14 poll options and a 26-comment thread on C's poll: B's root plus 25 alternating A/C replies, so the allowed tail extends beyond a 20-item reply page.
- 3 old unread notifications: B as actor, B as poll owner, and a C control row; 3 linked push jobs include pending and claimed/sending states.
- Request contexts describe guest, Bearer, and cookie sessions without storing real credentials or tokens.
- Four A/B decision states: neither direction, A→B, B→A, and both directions.

The former account for username reuse is metadata, not a second simultaneous `users.username` row. The current account is seeded with a new UUID; the old/new identity pair lets lifecycle tests assert that a repeated username does not inherit state.

```sh

```

Run the API/shared typecheck from the repository root:

```sh

```

These verify fixture construction and TypeScript only. They do **not** measure feed/search/comments latency or SQL query counts.

The existing pagination runner's load form is `node --import tsx scripts/pagination-load.mjs load <seed>`. It uses its own 100,000-poll/10,000-root/2,000-reply workload, 20-reader token file, and guarded test database; its output cannot be reported as this UB-03 dataset's complete baseline.
