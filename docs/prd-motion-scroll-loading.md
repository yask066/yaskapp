# PRD: Плавные реакции, появление карточек и стабильная прокрутка

**Продукт:** Yaskapp — Flutter mobile и web.  
**Дата:** 2 октября 2026 года.  
**Статус:** Draft for review; документ определяет требования, реализация не начата в рамках этой задачи.  
**Владелец:** Product / Engineering.  
**Главное ограничение:** не добавлять новые анимации до подтверждённой стабилизации логики и layout.

## 1. Проблема и результат

Пользователь должен видеть плавное изменение голосов и лайков, понятную загрузку и аккуратное появление карточек, сохраняя место в списке. Визуальные переходы не должны скрывать неправильные данные, повторные запросы или сдвиги layout.

Результат задачи — единые правила для Flutter и web: реакции сходятся с серверным состоянием, обновления не переносят пользователя в другую часть списка, загрузка занимает предсказуемое место, а motion добавляется только поверх проверенного поведения.

Успех оценивается по корректности данных, сохранению экранного якоря и измеренной производительности. Субъективная плавность дополняет эти проверки.

## 2. Основание и текущее состояние

Документ опирается на исходный код и [baseline T02](T02-motion-scroll-loading-baseline.md). Наблюдения baseline относятся к указанным в нём прогонам и не являются подтверждением исправлений на сегодняшний день.

| Область | Зафиксированное состояние | Следствие для задачи |
|---|---|---|
| Web media | `PollCard` выводит изображение без зарезервированной геометрии и error fallback; T02 наблюдает сдвиг после загрузки | Сначала закрепить размер media slot во всех состояниях |
| Web mutations | Ответы vote/like заменяют целую Poll в cache; T02 воспроизводит откат лайка поздним ответом vote | Устранить гонки до motion |
| Pending actions | Flutter Feed блокирует повторный like; web like не учитывает pending, а общий `isPending` влияет на голосование других карточек | Ввести состояние операции для конкретного опроса и действия |
| Loading | Web `AsyncState` показывает текст; многие Flutter-списки используют индикатор; notifications уже имеют отдельные loading-компоненты | Согласовать состояния и переиспользовать подходящие существующие компоненты |
| Feed pagination | Обе ленты загружают одну страницу; T02 проверяет две cursor-страницы мобильного поиска | Не вводить новую пагинацию ленты ради анимаций |
| Проверки | T02 фиксирует ошибки полного Flutter suite и отсутствие device/frame-time замеров | Критические ошибки затронутых сценариев и непроведённые замеры остаются условиями допуска |

T02 ссылается на исторические PRD 1.0 и `TASKS-motion-scroll-loading.md`, которых нет в текущем checkout. Этот документ не объявляет их задания выполненными. Идентификатор **AC-12** сохранён для требований производительности, чтобы существующий baseline оставался связан с приёмкой.

## 3. Цели и границы

### Входит

- Плавное изменение общего числа голосов, голосов вариантов, процентов, полос результатов и числа лайков опроса.
- Визуальное состояние like/unlike и выбранного варианта без изменения существующих правил голосования.
- Появление новых карточек опросов, результатов поиска, уведомлений и комментариев в существующих списках.
- Стабильная прокрутка при mutations, загрузке media, обновлении списка, существующей пагинации и возврате с дочернего экрана.
- Skeleton и loading/error/empty/retry для соответствующих экранов.
- Reduced motion, доступность, измерение производительности и управляемое включение motion.
- Исправления логики, cache и layout, которые необходимы для перечисленных сценариев. Изменения backend/shared contracts допустимы, если без них нельзя обеспечить корректную синхронизацию.

### Не входит

- Новые рекомендации, сортировки, infinite feed, новые пользовательские действия и изменение разрешений голосования.
- Редизайн экранов, новая система навигации, анимации всех модалок и route transitions.
- Новая доставка realtime-лайков или комментариев там, где её сейчас нет.
- Новая offline-очередь mutations, persistence позиции после перезапуска приложения или перезагрузки страницы.
- Анимированное удаление карточек, конфетти, частицы, звуки и haptics.
- Анимация счётчиков лайков комментариев; комментарии входят в требования появления, загрузки и scroll.
- Переход всей системы на optimistic updates и несвязанный рефакторинг.

### Матрица экранов

| Поверхность | Реакции опроса | Появление | Scroll и loading |
|---|---|---|---|
| Feed, списки опросов профиля, subscriptions/following | Где действия уже доступны | Карточки опросов | Да |
| Search / discovery | Где действия уже доступны | Опросы и пользователи | Да, включая существующую пагинацию |
| Poll detail | Да | Опрос при первой загрузке, новые комментарии | Да, включая клавиатуру и comment target |
| Notifications | Нет | Новые уведомления | Да, включая группы, read/unread и pagination |

Матрица применяется к существующим экранам двух клиентов: Flutter для Android и web. iOS исключён из текущего этапа и потребует отдельного scope/review; наличие Flutter iOS target не считается основанием включать его в acceptance matrix. Отсутствующая web-поверхность или недоступное действие не создаётся в этой задаче. Формы создания опроса, редактирования профиля и настройки остаются вне охвата.

## 4. Продуктовые решения

Выбран поэтапный подход: стабилизировать модель и геометрию, затем выпускать motion по группам сценариев. Он позволяет проверить, что плавность не ухудшает уже корректное поведение.

Альтернативы: добавление motion на всех экранах одновременно сокращает число этапов, но усложняет поиск причин скачков; одновременный переход на optimistic reactions даёт более ранний визуальный ответ, но расширяет задачу rollback и синхронизации. Эти варианты не выбраны.

По умолчанию новые реакции показывают pending сразу, а подтверждённый счётчик меняется после успешного ответа. Если на поверхности уже есть optimistic поведение, оно сохраняется только при доказанной корректности rollback и отсутствии двойного обновления после ответа/realtime.

## 6. Корректность реакций и состояния

### FR-01. Идентичность и область операции

- Карточка сохраняет идентичность по ID опроса/элемента; варианты — по ID варианта. Индекс и значение счётчика не используются как identity.
- Pending хранится по `pollId` и типу действия. Операция в одном опросе не блокирует другие опросы, навигацию, комментарии и прокрутку.
- Пока like/unlike выполняется, повторное нажатие игнорируется. Для vote/cancel действует одна выполняющаяся операция на опрос; повторные taps не создают новые запросы.
- Vote и like одного опроса могут выполняться параллельно. Их merge обязан сохранять оба результата независимо от порядка ответов.
- HTTP timeout, смена query/filter и уход с экрана не оставляют вечный pending и не применяют ответ к другой сессии или выдаче.

### FR-02. Согласованность источников

- Сервер остаётся источником истины. Анимация только отображает переход и не меняет domain state.
- Поздний ответ vote не перезаписывает более свежий like, и наоборот. Старый list/refetch response не откатывает более свежую mutation или realtime.
- Повторная доставка не прибавляет счётчик повторно. Broadcast агрегатов не сбрасывает персональные `viewerVoteOptionId` и `viewerHasLiked`.
- Все уже загруженные представления одного опроса обновляются согласованно, включая detail и применимые profile/search caches.
- Перед G0 должен быть зафиксирован и проверен контракт актуальности: версии/ревизии по независимым группам данных либо эквивалентный алгоритм merge, сохраняющий свежие поля. Простое сравнение времени получения полного snapshot не удовлетворяет требованию.
- Если текущий протокол не позволяет установить свежесть, необходимо расширить контракт или сериализовать конфликтующие операции и выполнить авторитетную HTTP-сверку; нельзя считать произвольный поздний snapshot актуальным.
- После reconnect/foreground и неоднозначного timeout выполняется сверка затронутого состояния. Новые realtime-каналы ради motion не добавляются.

### FR-03. Ошибки и границы

- При подтверждённом отказе сохраняется последнее подтверждённое состояние, показывается понятная ошибка и становится доступна повторная попытка.
- При неоднозначном результате нельзя слепо откатить или повторить действие: сначала сверка. Проверенный существующий optimistic слой откатывает только собственные поля и сохраняет более свежие данные.
- Поддерживаются like/unlike, разрешённые vote/cancel/change, закрытый опрос, удалённый опрос и истёкшая сессия. Задача не открывает недоступные сейчас действия.
- При нуле голосов проценты равны нулю; отрицательные значения, NaN и деление на ноль недопустимы. Согласованность total и вариантов проверяется до анимации.
- Округление процентов следует одной политике на обеих платформах; суммы округлённых значений могут отличаться от 100. Порядок вариантов от роста счётчика не меняется.

## 7. Стабильный layout и scroll

### FR-04. Геометрия карточки

- Media slot имеет размер до сетевого запроса и сохраняет его при success/error/retry. Используется существующее соотношение 16:9 с сохранением пропорций содержимого; другие отношения допустимы только с заранее известными размерами и резервированием до загрузки.
- Аватары и fallback имеют одинаковый размер. Загрузка шрифтов не вызывает позднюю смену геометрии видимых карточек.
- Области счётчиков и процентов выдерживают `9→10`, `99→100`, `999→1000` и обратные переходы. Формат крупных чисел и фиксируемая ширина определяются до G0; табличные цифры сами по себе недостаточны при увеличении разрядности.
- Иконка pending занимает тот же slot, что обычная иконка. Кнопки, подписи, выбранный вариант и полосы результатов не меняют высоту карточки при смене состояния.
- Поддерживаются длинные вопросы/варианты, узкий viewport и text scale 200%. Одинаковая высота всех карточек не требуется; требуется стабильная высота конкретной карточки при обновлении её состояния.

### FR-05. Сохранение позиции

Экранный якорь — ID первой видимой содержательной карточки и её вертикальная координата относительно верхней границы доступного viewport. При неизменном viewport допустимое смещение якоря после фонового обновления — не более **2 CSS px в web / 2 logical px во Flutter**. Измерение выполняется после завершения layout; во время теста нет пользовательского scroll.

- Реакции и загрузка media не меняют положение якоря.
- Append следующей страницы сохраняет текущие элементы и якорь; не выполняется замена списка на skeleton.
- Фоновое обновление не пересортировывает видимые карточки. Если поступает новый контент выше viewport, он накапливается за доступным действием «Новые элементы», где такой канал уже существует. Действие применяет обновление и явно переводит пользователя к началу.
- У вершины списка, в пределах 24 px от начала, новые элементы можно вставить автоматически с сохранением начала. Новая полоса уведомления об элементах не сдвигает viewport.
- Удаление элемента выше viewport компенсирует его высоту. При удалении якоря используется ближайший следующий сохранившийся элемент, иначе предыдущий; сохраняется его прежняя экранная координата, насколько позволяет граница списка. Пустой список показывает empty state.
- Refresh сохраняет старый контент до ответа и существующий якорь, если элемент остаётся в выдаче. При смене query/filter/sort допускается намеренный переход к началу новой выдачи.
- Для одинакового контекста список → detail/comments/profile → назад восстанавливаются загруженные страницы, query/filter и якорь. Восстановление немедленное, без smooth-scroll и повторной entry-анимации старых элементов.
- Контекст позиции включает route/экран, тип списка, query, filter/sort и пользователя. При logout или смене пользователя данные позиции очищаются.
- Открытие клавиатуры или изменение viewport может изменить координату якоря; приоритет — видимость composer/фокуса и отсутствие непреднамеренного перехода в начало. Закрытие клавиатуры возвращает читаемое место, если контент сохранился.
- Явный переход к comment target и действие «Новые элементы» имеют приоритет над восстановлением старого якоря. Motion не меняет существующее поведение unread/read или auto-scroll комментариев.

## 8. Skeleton и loading states

### FR-06. Матрица состояний

| Состояние | Поведение |
|---|---|
| Initial load без данных | Статический skeleton соответствующего типа, шапка и навигация доступны |
| Данные уже в cache | Сразу показать данные; не мигать skeleton перед background refetch |
| Refresh/refetch | Сохранить контент; компактный индикатор в заранее выделенном месте |
| Loading more | Сохранить список; индикатор/placeholder в footer; защита от двойной загрузки |
| Pending mutation | Индикатор внутри неизменного slot действия; остальные карточки доступны |
| Empty после успешного ответа | Контекстный empty state; skeleton отсутствует |
| Initial error/timeout | Error state с Retry; skeleton завершён |
| Refresh/load-more error | Контент сохранён; локальная ошибка и Retry без сброса позиции |
| Media loading/error | Slot и fallback одинаковой геометрии; повторное получение не схлопывает карточку |

Skeleton повторяет основные области poll/user/comment/notification row. Для неизвестного содержимого он использует репрезентативную геометрию; точное совпадение с неизвестной длиной текста не обещается. Переход первой загрузки к данным не сбрасывает scroll; измеримый предел 2 px применяется к уже существующим содержательным элементам, а не к вымышленному ID skeleton.

Резервирование loading-области начинается сразу. Skeleton показывается после 150 мс ожидания, чтобы быстрый ответ не создавал вспышку. Искусственной минимальной длительности нет: готовые данные отображаются сразу. Срок ожидания read-запроса — 10 секунд до retryable timeout; серверные deadlines и особенности существующих mutations сохраняются. Поздний ответ истёкшего запроса не замещает результат новой попытки.

До G0 skeleton статический. После G0 мягкий shimmer разрешён как необязательное улучшение; он отключается при reduced motion, вне viewport и в фоне. Retry не запускается автоматически в бесконечном цикле.

## 9. Правила motion после G0

### FR-07. Единые параметры

Начальные параметры являются требованиями первой версии. Их допустимо уточнить по профилированию с фиксацией изменения; Flutter и web сохраняют сопоставимый характер переходов.

| Переход | Длительность и характер | Ограничение |
|---|---|---|
| Счётчики голосов/лайков, проценты | 180 мс, ease-out; короткий crossfade старого и нового значения | Переход в зарезервированном slot, без перебора промежуточных чисел |
| Полоса результата | 240 мс, ease-out от текущего отображённого значения к новому | Размер контейнера неизменен |
| Like/unlike и selected state | 160 мс, смена цвета/иконки; scale до 1.08 только для локального действия | Без движения соседей, без повторного pulse на broadcast |
| Появление карточки | 200 мс, opacity 0→1 и translateY 8→0 | Окончательный размер занимает место до начала эффекта |
| Каскад первой группы | Интервал 35 мс, максимум первые 6 видимых карточек | Общая последовательность до 400 мс |
| Skeleton → content | Crossfade до 120 мс, допускается совместить с entry | Один переход, без двойной анимации |

Для больших чисел отображаются старое и новое значение, а не каждый промежуточный шаг. После завершения визуальное значение точно соответствует последнему принятому состоянию. Семантический счётчик обновляется сразу и не следует кадрам анимации.

### FR-08. Прерывание и повторение

- Новое значение во время перехода заменяет цель; продолжение идёт от текущего отображённого состояния. Очередь старых анимаций не накапливается.
- Первый показ данных задаёт исходные числа сразу; счётчики не анимируются от нуля при каждом mount.
- Entry выполняется один раз на ID в текущем контексте списка. Rebuild/refetch, возвращение назад, повторный вход карточки во viewport и virtualized remount не повторяют эффект.
- Для новой страницы анимируются только новые видимые элементы; существующие не исчезают. Элементы, смонтированные вне viewport, показываются без отложенного эффекта при дальнейшем scroll.
- Первая группа в новом query/filter может появиться с entry. Смена данных не анимирует высоту всего списка.
- Появление не задерживает доступность действий, keyboard focus и hit testing; выполняется только визуальный переход.
- В фоне и после dispose/unmount не остаются активные animation controllers, timers или подписки этой функции.

## 10. Доступность и reduced motion

- Web учитывает `prefers-reduced-motion`; Flutter — системный запрос отключения анимаций. Изменение настройки применяется без перезапуска экрана.
- При reduced motion count/bar/entry/scale/shimmer и программный smooth-scroll отключены. Изменения отображаются немедленно, static skeleton и текст загрузки остаются.
- Загрузка имеет одно понятное status/semantics-сообщение на область; декоративные skeleton и копии цифр скрыты от screen reader.
- Локальный успешный результат и ошибка озвучиваются один раз. Массовые realtime-обновления не создают поток live-announcements.
- Выбор, like и pending различимы семантически, а не только цветом. Focus сохраняется при обновлении и восстановлении списка.
- Motion не ухудшает существующие touch targets, контраст и keyboard navigation. Проверяются text scale 200%, клавиатура web, Android TalkBack и доступное дерево web.

## 11. Технические границы

Domain state, layout и motion должны быть независимо проверяемыми. Отключение motion не меняет запросы, merge, selected state, размер карточки или восстановление позиции.

- Общие motion tokens и reusable presentation-компоненты применяются в пределах каждого клиента; Flutter и web не обязаны использовать одинаковую библиотеку.
- Во Flutter проверяются identity Sliver/List элементов, сохранение scroll context, rebuild scope и lifecycle controllers. В web — keys, query caches, per-poll pending, browser scroll restoration и font/media loading.
- Анимируются ограниченные presentation-свойства. Нельзя запускать тяжёлый rebuild/refetch всей ленты ради кадра анимации или делать переход высоты карточки способом компенсации layout shift.
- Переключатели `reactionsMotion` и `entryMotion` управляют эффектами независимо. Disabled соответствует стабилизированной версии; reduced motion имеет приоритет. Статические loading states не зависят от этих переключателей.
- Необходимые изменения freshness/backend contracts совместимы с существующими клиентами и документируются до реализации этапа B.

## 13. Проверки и acceptance criteria

### Общая фикстура и сценарии

Расширить существующую T02-фикстуру: длинный текст, ноль голосов, равные результаты, крайние проценты, отсутствующее/медленное media, `9/10`, `99/100`, `999/1000`, разные размеры экрана и text scale. Для уже существующей пагинации — две страницы с пересекающимся ID. Для производительности — повторяемый набор из 100 уникальных элементов, без добавления feed pagination в продукт.

Обязательные network-сценарии: normal, задержка 2 с, read timeout, retry, offline/error, vote-start → like-finish → vote-finish и обратный порядок, realtime между запросом и ответом, повторное событие, stale refetch, rapid taps, logout/unmount с поздним ответом. T02 mock не поддерживает realtime: эти случаи проверяются отдельным управляемым harness или integration backend.

### Критерии

| ID | Критерий и доказательство |
|---|---|
| AC-01 | Ни одна новая motion-группа не добавлена до отчёта G0; порядок подтверждён результатами этапов |
| AC-02 | 10 быстрых taps pending like или vote создают один выполняющийся запрос соответствующей операции; другой опрос остаётся доступен |
| AC-03 | Все reordered/realtime/stale сценарии сохраняют свежие независимые поля и сходятся с сервером; duplicate не меняет итог повторно |
| AC-04 | Счётчики, проценты, pending и media success/error не меняют высоту уже показанной карточки и координаты соседних действий более чем на 2 px; text scale 200% без overflow |
| AC-05 | Background updates, append, удаление выше viewport и refresh сохраняют якорь в пределах 2 px; правила удаления самого якоря и новых элементов соблюдены |
| AC-06 | Возврат с detail/comments/profile восстанавливает контекст, страницы и якорь в пределах 2 px при неизменном viewport; old entry не повторяется |
| AC-07 | Новые query/filter/sort, keyboard и comment target соблюдают явные исключения FR-05; нет случайного reset в начало |
| AC-08 | Все состояния FR-06 проверены; нет skeleton поверх cache, потери контента при ошибке или loading без выхода по deadline |
| AC-09 | Числа и полосы достигают последней цели, новые значения прерывают предыдущую цель; анимация не создаёт запросов и не меняет data state |
| AC-10 | Entry только для допустимых новых видимых ID, без повторов при remount/back/refetch; layout не участвует в переходе |
| AC-11 | Reduced motion немедленно отключает эффекты; semantic value обновляется один раз, decorative duplicates не озвучиваются; focus и navigation сохранены |
| AC-12 | На каждой заявленной тестовой конфигурации не более 1% кадров дольше бюджета и прирост относительно стабилизированной версии без motion не более 0,5 процентного пункта; протокол ниже |
| AC-13 | После 20 циклов list → detail → back нет накопления controllers/listeners/timers этой функции и повторных запросов из-за анимации; скрытый экран не продолжает её работу |
| AC-14 | Выключение двух motion flags возвращает статическое представление с той же логикой, геометрией и scroll; smoke с flags on/off проходит |
| AC-15 | Целевые автоматические и сквозные проверки обеих платформ проходят; связанные failures T02 устранены, непроведённые проверки обозначены явно |
| AC-16 | Сохранены отчёты G0 и финального сравнения, перечень конфигураций, известные ограничения и инструкция выключения motion |

### Протокол AC-12

- Матрица текущего этапа: Android 60 Hz и доступный режим до 120 Hz, Chromium desktop 1440×900 и responsive 390×844. iOS отложен и не является блокером текущих M17/G0. Сохраняются реальные модель, OS/browser/build, частота, DPR, CPU/GPU и режим энергосбережения. Reference-матрица T02 служит ориентиром; версии из неё не считаются фактически установленными.
- Flutter измеряется в profile mode на устройстве; web — в production build. Debug, widget tests и эмуляция узкого viewport не заменяют device profiling.
- Для каждой пары motion off/on одинаковые fixture, cache/network policy и viewport. Три прогона по 30 секунд: scroll через набор, серия реакций и обновлений; дополнительно отдельно первый load с skeleton. Сохранить trace и число кадров за бюджетом для каждого прогона.
- Бюджет определяется фактической частотой: около 16,7 мс при 60 Hz, 8,3 мс при 120 Hz. Для адаптивной частоты записываются интервалы/режим; нельзя автоматически применять 8,3 мс ко всему trace.
- Учитываются доля late/janky frames, p95 и максимальная длительность, scope rebuild/layout. Во Flutter используется timeline с учётом UI/raster; в web — frame trace и long tasks. Метод классификации кадров фиксируется одинаково для off/on; UI и raster duration не суммируются произвольно.
- Порог применяется к каждому прогону. Смещение якоря измеряется отдельно; отсутствие заметного скачка на видео не заменяет числовую проверку.
- Нет устройства или trace — статус «не измерено» и закрытый допуск соответствующего этапа. Заявлять выполнение AC-12 по успешным unit/widget tests нельзя.

## 14. Риски и решения

| Риск | Решение |
|---|---|
| Snapshot не несёт достаточной информации о свежести | Зафиксировать и проверить merge/contract в A2; при необходимости совместимое backend-расширение |
| Skeleton отличается от длинного реального содержимого | Репрезентативные шаблоны; сохранять реальные данные при refetch; не обещать точного совпадения неизвестного текста |
| Сохранённый offset неверен после удаления/изменения текста | Использовать ID + экранную координату и fallback-якорь, а не только абсолютный offset |
| Virtualization повторяет entry | Учёт увиденных ID по контексту, очистка при смене сессии/выдачи |
| Motion ухудшает frames или расход в фоне | Ограничить видимые эффекты, отключать вне viewport; shimmer необязателен |
| Существующие failures скрывают регрессии | Разобрать failures по охвату, исправить связанные и документировать остальные до G0 |
| Недоступен тестовый парк | Сохранить честный статус; не обходить G0 предположением о производительности |

## 15. Выпуск и Definition of Done

Сначала выпускается стабилизированная версия со статическими loading states и motion flags off. После G0 реакции включаются на проверенных сборках, затем entry; перед расширением включения повторяются критические scroll/error/reduced-motion сценарии и AC-12. При регрессии flags отключаются без отката исправлений состояния и layout.

Задача завершена, когда выполнены AC-01–AC-16, все поверхности из матрицы проверены на соответствующих клиентах, нет известных ошибок корректности и scroll в охвате, измерения соответствуют порогам и сохранены воспроизводимые отчёты. Наличие PRD или работающей демонстрации motion само по себе не означает завершение реализации.
