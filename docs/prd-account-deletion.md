# PRD: Самостоятельное удаление аккаунта и очистка данных

**Продукт:** Yaskapp  
**Дата:** 2026-10-12  
**Статус:** Draft для продуктового ревью  
**Область:** API, Flutter, публичный web-клиент, хранение данных и эксплуатация

**Изменение требований 2026-10-18:** пользователь запросил закрытый архив
модерации на 30 дней после удаления для разбора нарушений и IP-блокировки.
В основной БД сохраняются идентификаторы/профиль, недавние записанные IP и
материалы связанных нарушений. Доступ только superadmin; повторное удаление
не продлевает срок. На границе 30 дней архив недоступен, затем worker удаляет
его вместе с аудитом доступа. IP-блокировки сохраняются отдельно до отмены.
Пароли, сессии, токены и медиа исключены. Это уточняет исходный draft ниже;
срок удаления резервных копий этим изменением не утверждается.

**Статус решений:** исходный запрос подтверждает самостоятельное удаление
аккаунта с очисткой данных. Сроки хранения, доступные исключения, особенности
голосов и обсуждений ниже предложены для продуктового решения; пока они не
утверждены и не должны считаться обещанием пользователям.

Детальный [контракт API](account-deletion-api.md) и [карта данных](account-deletion-data-map.md)
ведутся отдельно от этого продуктового описания.

## 1. Проблема и результат

Пользователь должен самостоятельно удалить свой аккаунт и связанные с ним
данные без обращения в поддержку. После подтверждения аккаунт сразу перестаёт
быть доступен, все его сессии прекращаются, а система доводит очистку до конца
даже при сбое storage или перезапуске сервиса.

Существующая административная операция только устанавливает `status = 'deleted'`
и `deleted_at`. Она не обеспечивает очистку персональных данных, контента и
файлов. Для нового сценария одной такой отметки недостаточно.

**Принятое допущение:** «очистка данных» означает очистку при удалении аккаунта.
Отдельная очистка истории с сохранением аккаунта в этот PRD не входит.
Сроки и правила хранения ниже — предлагаемые продуктовые решения, а не
утверждение о действующей политике или требованиях законодательства.

## Статус продуктовых решений

| Решение | Статус | Временное правило реализации |
| --- | --- | --- |
| Пользователь может сам удалить аккаунт и связанные данные | Подтверждено исходным запросом | Проектировать единую операцию аккаунта с очисткой связанных данных |
| Клиенты первого релиза — Flutter и публичный web | Предложение PRD, требует проверки объёма релиза | Контракт API не зависит от интерфейса |
| Нужна отдельная очистка данных с сохранением аккаунта | Не решено | Не включать в план этой функции; при выборе требования завести отдельную задачу |
| Удаление необратимо и начинается после повторного подтверждения паролем | Предложение к подтверждению | Использовать до решения владельца продукта; период восстановления не реализовывать |
| Полное удаление голосов из закрытых опросов | Предложение к подтверждению | Не оставлять фиктивные голоса; подтвердить влияние на сохранённые результаты |
| Сохранение чужих ответов в чужих опросах при перепривязке | Предложение к подтверждению | Сохранять только ответы и авторство других активных пользователей; подтвердить UX |
| Очистка активных хранилищ за 24 часа; backup за 30 дней; завершённый журнал за 35 дней; идентифицируемая история модерации за 30 дней | Предлагаемые сроки, требуют решения владельца продукта и согласования политики хранения | Не показывать эти сроки как гарантированные, пока они не утверждены и технически не подтверждены |
| Правило для пользовательских жалоб и содержимого модерации | Предлагаемая матрица в разделе 6, требует подтверждения владельца продукта | До утверждения не сохранять дополнительную идентифицируемую историю на основании предположений |
| Повторная регистрация с прежними email/username после очистки | Предложение к подтверждению | При удалении освобождать идентификаторы после завершения очистки; создание аккаунта использует новый ID |

Пока решения помечены как предложенные, формулировки сроков в интерфейсе и
публичной политике не включать. Для выпуска требуется явно утвердить их и
подтвердить, что backup, хранилища и эксплуатация способны выполнить сроки.

## 2. Цели и границы первого релиза

- Понятный сценарий удаления в Flutter и публичном web-клиенте.
- Защита от случайного удаления и удаления чужого аккаунта.
- Немедленное прекращение доступа и публичного отображения данных.
- Полная очистка действующих хранилищ с контролируемыми повторными попытками.
- Сохранение корректных счётчиков и чужих обсуждений там, где опрос остаётся.
- Проверяемый результат и понятные сроки для пользователя.

Не входят: деактивация, период восстановления, отмена принятого удаления,
экспорт данных, выборочное удаление категорий, обязательный опрос о причинах
ухода, изменение административного удаления и автоматическая очистка всех
ранее удалённых администраторами аккаунтов. Последнее требует отдельного
решения о миграции существующих данных.

## 3. Контекст проекта

| Существующий механизм | Что учитывать при доработке |
| --- | --- |
| `users.status`, `deleted_at`, `session_version` | Использовать для немедленного закрытия доступа; затем физически удалить аккаунт |
| Native Bearer JWT и web HttpOnly cookie | Прекратить обе разновидности сессий на всех устройствах |
| Flutter `SettingsScreen`, web `MyProfilePage` | Добавить доступное действие удаления в существующие экраны |
| PostgreSQL и `ON DELETE CASCADE` | Каскады не пересчитывают прикладные счётчики и могут удалить чужие ответы |
| S3/MinIO и поля object key | Файлы нужно удалять отдельно, включая ранее заменённые и оставшиеся без ссылки |
| Notifications, JSON payload, устройства и push jobs | Очистить копии имён и контента, отключить доставки и удалить токены устройств |
| Reports, appeals, sanctions, audit | Проверить ссылки без FK, свободный текст и metadata; простого удаления `users` недостаточно |
| WebSocket и Redis bus | Завершать сессии и распространять изменения между всеми API-процессами |
| Резервные копии PostgreSQL | Установить срок хранения и исключить возвращение удалённых данных после restore |

## 4. Пользовательские истории

1. Как пользователь, я нахожу удаление аккаунта в настройках и понимаю,
   какие данные исчезнут и когда.
2. Как пользователь, я подтверждаю владение аккаунтом и явно соглашаюсь
   с необратимым удалением.
3. Как пользователь, я могу отменить действие до отправки подтверждения.
4. Как пользователь с нестабильной сетью, я могу узнать результат запроса,
   не запуская удаление повторно и не получая ложное сообщение об успехе.
5. Как другой пользователь, я вижу корректные результаты опросов,
   подписки и сохранившиеся ответы после удаления аккаунта.

## 5. Пользовательский сценарий

### Вход и подтверждение

Flutter: `Profile → Settings → Delete account`. Web: отдельный блок
`Delete account` в собственном профиле. Действие визуально отделено от выхода
и удаления аватара. Текущий интерфейс приложения на английском; тексты нового
сценария должны следовать языку соответствующего клиента.

Экран удаления сообщает:

- Будут удалены аккаунт, профиль, аватар, опросы, комментарии, голоса,
  лайки, подписки и настройки уведомлений.
- Вместе с собственными опросами исчезнут обсуждения и действия других
  пользователей внутри этих опросов.
- Доступ закрывается сразу; очистка действующих хранилищ занимает до 24 часов.
- Резервные копии могут содержать данные до 30 дней; минимальные служебные
  записи об удалении — до 35 дней. Подробности доступны по ссылке на политику.
- Восстановить аккаунт и контент после подтверждения нельзя.

Для продолжения требуется текущий пароль и явное подтверждение
`I understand that this action cannot be undone`. До выполнения этих условий
финальная кнопка `Delete my account` недоступна. Не требовать причины ухода,
перехода в поддержку или дополнительных экранов удержания.

### Отправка и результат

1. Клиент проверяет пароль на сервере и получает краткоживущее разрешение
   только на удаление и квитанцию для проверки результата.
2. После финального нажатия блокирует повторную отправку и показывает прогресс.
3. Сервер атомарно принимает операцию, закрывает доступ и сохраняет задачу очистки.
4. Клиент очищает сессию и данные аккаунта, закрывает приватные экраны и показывает:
   `Your account is closed. Data deletion is in progress and will finish within 24 hours.`
5. Статус `completed` означает, что очистка действующих хранилищ завершена.
   До этого нельзя показывать `All your data has been deleted`.

После принятия операции восстановление входом, отмена и кнопка «Назад»
не возвращают аккаунт. Регистрация с теми же email/username возможна после
завершения очистки, создаёт новый `userId` и не возвращает прежние данные.

### Ошибки и особые случаи

| Ситуация | Поведение |
| --- | --- |
| Неверный пароль | Ошибка у поля; аккаунт и данные не изменяются |
| Нет сети до отправки | Удаление не начинается; можно повторить |
| Потеря ответа после отправки | Показать «Проверяем результат», запросить статус по квитанции; не считать общий `401` доказательством удаления |
| Повторное нажатие или повтор запроса | Та же операция, без повторных списаний счётчиков |
| Ошибка до фиксации операции | Аккаунт остаётся доступным; понятная ошибка и возможность повторить |
| Ошибка очистки после принятия | Аккаунт остаётся закрытым; очистка продолжается автоматически |
| Перезапуск приложения | Приватные данные не восстанавливаются; незавершённый запрос проверяется по квитанции |
| Заблокированный аккаунт или действующая санкция | Разрешена проверка пароля только для удаления; обычная сессия и доступ к контенту не выдаются |
| Последний действующий superadmin | Удаление запрещено с объяснением необходимости передать роль; проверка выполняется сервером |

Для остальных ролей не требуются административные permissions. При удалении
модератора освободить назначенные ему дела. Потерянный пароль обрабатывается
существующим механизмом восстановления, если он доступен; новый механизм
восстановления пароля не входит в эту задачу.

## 6. Что удалять и что сохранять

| Категория | Требуемое поведение |
| --- | --- |
| Аккаунт и профиль | Физически удалить `users` и `profiles`, включая email, username, password hash, имя, bio, страну и остальные поля профиля |
| Файлы | Удалить аватар и все принадлежащие аккаунту медиа, если присутствуют, включая старые объекты, версии и orphan-файлы; чужие объекты не трогать |
| Собственные опросы | Удалить опросы, варианты, все связанные голоса, лайки, комментарии и ответы; включить ранее скрытый и soft-deleted контент |
| Комментарии в чужих опросах | Удалить текст, авторство и реакции на свои комментарии; чужие ответы сохранить и перепривязать к ближайшему сохранившемуся предку или в корень |
| Голоса в чужих опросах | Удалить записи голосования, уменьшить счётчики вариантов и опросов, обновить проценты |
| Лайки | Удалить свои лайки; пересчитать счётчики у сохранившихся опросов и комментариев |
| Подписки | Удалить связи в обоих направлениях; пересчитать followers/following у оставшихся пользователей |
| Уведомления | Удалить полученные уведомления и уведомления других пользователей, где удаляемый аккаунт — actor либо target — удаляемый контент; удалить связанные push jobs, пересчитать unread |
| Push и предпочтения | Удалить привязки устройства, push-токены, настройки уведомлений; не посылать новые push для удаляемых данных |
| Жалобы и апелляции пользователя | Удалить пользовательский свободный текст и записи; сохранить только допустимую минимальную служебную историю по правилам ниже |
| Жалобы других пользователей и модерация | Сохранить чужие обращения и результат обработки; удалить копии профиля и удаляемого контента, очистить metadata и ссылки, отображать недоступную цель |
| Кэш и поиск | Удалить контролируемые системой копии профиля и контента, поисковые записи и производные данные; не возвращать их по прямому URL |
| Локальные данные | Очистить токены, профиль, ленты, уведомления, черновики, кэш медиа и приватную навигацию, где такие данные хранятся |

**Голоса в закрытых опросах тоже удаляются.** Это явное исключение из правила
обычной отмены голоса после `endsAt`: очистка аккаунта меняет итоговые результаты.
Не оставлять голос с заменой `voter_id` на фиктивного пользователя.

**Чужие ответы в сохраняемых опросах не удаляются каскадом.** Перепривязать их
до физического удаления родителя и пользователя; пересчитать `comments_count`,
`replies_count`, лайки и применимые revisions. Политика отличается от удаления
целого собственного опроса, где исчезает обсуждение целиком.

Очистка не обещает удалить чужие пересказы, скриншоты или уже доставленные
уведомления на чужих устройствах. Система удаляет свои копии и не создаёт новые.

## 7. Сроки, служебные записи и резервные копии

Предлагаемые сроки, подлежащие утверждению до выпуска:

| Объект | Срок и условия |
| --- | --- |
| Доступ, новые запросы и доставки | Закрываются при фиксации принятой операции |
| Действующие БД, storage, серверные кэши | Полная очистка не позднее 24 часов после принятия |
| Резервные копии, реплики backup и архивные версии | Остаточные данные истекают не позднее 30 дней после принятия; сроки должны выполняться во всех местах хранения |
| Журнал завершённых операций и запретов восстановления | До 35 дней после принятия, затем автоматическая очистка |
| Минимальная история модерации о данном аккаунте | До 30 дней после принятия, затем очистка связанных остаточных идентификаторов |

Минимальная запись удаления содержит идентификатор операции, прежний `userId`,
время и этапы обработки, результат и технические коды ошибок. В ней нет email,
username, пароля, токенов, IP, текста профиля или контента. Это служебная запись
с ограниченным доступом; наличие UUID не делает её полностью анонимной.
Ключи файлов разрешены только в защищённом манифесте очистки и удаляются после
успешной обработки соответствующих объектов.

Незавершённая задача и её манифест не удаляются по TTL: они нужны для завершения
очистки. Если сбой выходит за указанный срок хранения служебных записей,
эксплуатация устраняет его как нарушение срока; после завершения просроченные
технические записи удаляются без нового периода хранения.

В истории модерации допустимы даты, типы действий и результаты. Свободный текст,
JSON snapshots, причины и metadata проверяются на копии удаляемых данных.
Бессрочно сохранять их под видом аудита нельзя. Исключения для обязательного
хранения должны иметь конкретные категории, основание, срок и отражение
в политике до релиза; в базовом сценарии таких исключений не предполагается.

При восстановлении backup до открытия трафика применить актуальный журнал
удалений и повторно выполнить очистку. Этот журнал должен переживать restore
основной БД. Проверять восстановление вместе с object storage и кэшами.
Обычный rollback приложения не отменяет принятые удаления.

Сторонние браузерные кэши истекают по сроку уже выданного ответа; текущий
endpoint аватара использует `max-age=300`. Для новых запросов после принятия
удаления backend не должен выдавать изображение.

## 8. Требования к обработке на сервере

### Принятие операции

- Определять аккаунт по проверенной сессии/подтверждению пароля; клиент не
  передаёт произвольный `userId` для удаления.
- Проверять пароль, принадлежность разрешения и защиту последнего superadmin
  на сервере. Для cookie-запросов сохранять проверку доверенного Origin.
- В одной транзакции закрыть аккаунт, инвалидировать сессии, запретить новые
  действия и сохранить устойчивую задачу очистки. Если транзакция откатилась,
  удаление не считается принятым.
- После принятия исключить профиль и контент из лент, поиска, уведомлений,
  списков подписок, прямых API-запросов и media endpoints. Проверять владельца
  и состояние аккаунта, пока фоновые операции ещё не удалили строки.
- Завершить открытые WebSocket-соединения во всех процессах; повторный
  handshake и все виды авторизованных запросов должны быть отклонены.
- Действия, начатые до закрытия, не могут записать новые данные после него.
  Это относится к голосам, комментариям, upload, регистрации устройства,
  push worker и модерации. Учесть уже загруженные, но ещё не привязанные файлы.

### Очистка и восстановление после сбоев

- Состояния операции: `pending`, `processing`, `retrying`, `completed`.
  Ошибка не возвращает пользователя в `active`.
- Сохранить манифест принадлежащих аккаунту файлов до удаления ссылок в БД.
  Отдельно проверять частичные ошибки пакетного удаления и версии объектов.
- Шаги идемпотентны: отсутствующий объект уже очищен, счётчики не уменьшаются
  второй раз. Использовать фактические оставшиеся записи для проверки итогов.
- Повторять временные ошибки с увеличением интервала. При сбое дольше часа
  уведомить эксплуатацию; после 24 часов зафиксировать нарушение срока.
  Ни исчерпание попыток, ни перезапуск не теряют задачу.
- Большие аккаунты обрабатывать порциями без длительной блокировки API.
- Доставлять события удаления и обновлённые счётчики после фиксации изменений;
  учитывать существующие revisions и работу нескольких API-процессов.
- `completed` выставлять только после проверки БД, файлов, управляемых копий,
  связей и счётчиков. Ожидание истечения backup не блокирует этот статус,
  поскольку его значение явно ограничено действующими хранилищами.

## 9. Контракты API

Предварительные endpoint names и поля для разработки зафиксированы в
[контракте API](account-deletion-api.md). Пользовательские обещания и сроки
остаётся брать из раздела «Статус продуктовых решений» выше: контракт API не
утверждает продуктовые сроки и исключения.

Имена маршрутов предварительные; поведение обязательно для всех клиентов.

| Метод и маршрут | Назначение и результат |
| --- | --- |
| `POST /auth/account-deletion/verification` | Проверка текущего пароля; для обычной сессии аккаунт определяется сервером, без сессии нужны login и password. Выдаёт `deletionToken` на 10 минут и `statusToken` на 48 часов, связанные с одной операцией |
| `DELETE /auth/me` | Авторизация специальным `deletionToken`, явное `confirm: true`. Возвращает `202` с `operationId`, статусом и сроком завершения; очищает session cookie |
| `GET /auth/account-deletion/status` | Авторизация `statusToken`; возвращает только состояние своей операции, время принятия и срок очистки. До принятия — `not_started` |

Специальные токены не подходят для обычного API. `statusToken` не позволяет
начать или отменить удаление, получить профиль либо узнать наличие чужого
аккаунта. Передавать токены в заголовках, не в URL; не логировать их и пароль.
Хранить на сервере только безопасные проверочные значения токенов.

Повтор запроса с тем же разрешением возвращает ту же операцию, даже если
обычная сессия уже отозвана. Новая проверка не создаёт вторую активную операцию
для того же аккаунта. Подписанная квитанция/её запись должны работать после
физического удаления `users`.

Различать ошибки неверного подтверждения, неверных credentials, истёкшего
разрешения, превышения частоты, последнего superadmin и временной недоступности.
Неверный пароль на экране удаления не должен запускать общий logout-код
клиента. Для проверки пароля: максимум 5 неуспешных попыток за 15 минут на
аккаунт плюс ограничение по IP; ответ `429` содержит `Retry-After`.

Клиент сохраняет квитанцию до отправки финального запроса, чтобы пережить
потерю ответа. Она хранится отдельно от данных аккаунта, не содержит профиль
и удаляется после завершения или истечения 48 часов. Истечение квитанции
не отменяет серверную очистку.

## 10. Требования к клиентам

- Flutter очищает secure storage, состояние аккаунта, локальные данные,
  подписки realtime и navigation stack. Web очищает session state,
  query cache и приватную историю переходов; сервер отзывает cookie.
- При локальном сбое очистки не открывать приватные экраны; повторить очистку
  до восстановления обычного интерфейса. Ошибка локального storage не
  отменяет принятую серверную операцию.
- Запоздалые ответы и события не возвращают данные аккаунта в кэш.
- Другие активные устройства и вкладки очищают состояние при отзыве сессии;
  устройство, находившееся offline, делает это при следующей проверке доступа.
- Чужие клиенты удаляют недоступный контент и обновляют счётчики по realtime;
  при пропущенных событиях сверяются с сервером после reconnect/refetch.
- Диалоги доступны с клавиатуры и screen reader, имеют управляемый фокус,
  видимые ошибки и состояние загрузки. Удаление не зависит только от цвета.

## 11. Критерии приёмки

| ID | Проверка |
| --- | --- |
| AC-01 | В Flutter и web есть доступный вход в сценарий; предупреждение содержит состав данных, сроки, необратимость и судьбу обсуждений собственных опросов |
| AC-02 | Отмена до отправки и неверный пароль не меняют данные; удалить чужой аккаунт заменой параметров/токена нельзя |
| AC-03 | После принятия старые Bearer JWT и cookie не дают доступа ни на одном устройстве; sockets закрываются, новые подключения отклоняются |
| AC-04 | Профиль, собственный контент и медиа недоступны по новым запросам сразу после принятия, включая поиск, списки, прямые URL и soft-deleted объекты |
| AC-05 | После `completed` нет строк аккаунта/профиля и принадлежащих ему данных в действующих хранилищах, кроме явно ограниченных служебных записей |
| AC-06 | Storage очищен от текущих, заменённых, orphan- и версионных объектов; частичная ошибка batch-delete не даёт ложного `completed` |
| AC-07 | Голоса и лайки в чужих опросах удалены; счётчики, проценты, revisions, followers/following, replies и unread соответствуют оставшимся данным и не отрицательны |
| AC-08 | Голос удаляется и из закрытого опроса; чужие ответы в сохраняемом опросе остаются доступны с корректной структурой |
| AC-09 | Удаление собственного опроса очищает его обсуждение целиком; уведомления и их payload не раскрывают удалённый профиль или контент |
| AC-10 | Повторы, параллельные запросы и потеря ответа дают одну операцию; результат проверяется после отзыва обычной сессии и удаления `users` |
| AC-11 | Сбой БД до принятия сохраняет аккаунт; сбой storage/Redis или restart после принятия сохраняет закрытие и возобновляет очистку |
| AC-12 | Гонки с голосованием, комментарием, upload, push и модерацией не создают новые остаточные данные и не ломают счётчики |
| AC-13 | После logout, reload, back navigation, смены пользователя и поздних ответов клиент не показывает данные удалённого аккаунта |
| AC-14 | Заблокированный пользователь может подтвердить удаление без обычного входа; последний superadmin защищён и при параллельном изменении ролей |
| AC-15 | Audit, reports, appeals и metadata очищены по матрице; чужие обращения сохраняются без копий удаляемых данных |
| AC-16 | На staging подтверждены сроки очистки и expiry, автоматические повторы, сигнал о просрочке и restore без восстановления удалённого аккаунта |
| AC-17 | Повторная регистрация после очистки создаёт новый аккаунт без прежнего контента, связей, устройств и уведомлений |

## 12. Метрики и условия выпуска

Считать без паролей, токенов и содержимого пользовательских данных:

- количество принятых, завершённых и повторяемых операций;
- время от принятия до завершения: p50, p95, максимум;
- число операций старше 1 часа и нарушений срока 24 часа;
- ошибки по этапам БД, storage, кэша и обновления клиентов;
- расхождения счётчиков и число найденных остаточных объектов.

Целевые показатели: 100% принятых операций сразу закрывают серверный доступ;
не менее 99% завершают очистку в пределах 24 часов. Любая просроченная операция
остаётся в очереди и требует реакции эксплуатации; целевой показатель не
разрешает терять оставшийся 1% задач.

Перед релизом подтвердить продуктовые сроки хранения и правила модерации,
опубликовать согласованные тексты политики, настроить worker и мониторинг,
выполнить AC-01–AC-17 на staging с тестовым аккаунтом, чужими ответами,
закрытым опросом и отказом storage. Ограниченное включение функции не должно
отключать worker уже принятых операций.

Открытые продуктовые вопросы: нужна ли отдельная очистка без удаления аккаунта;
утверждаются ли предложенные сроки 24 часа / 30 дней / 35 дней; нужны ли
конкретные исключения хранения. До изменения решений реализация ориентируется
на описанный сценарий; выпуск требует согласованной политики хранения.
