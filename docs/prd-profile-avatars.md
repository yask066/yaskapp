# PRD: Аватары профиля

## Краткое описание

Добавить полноценную систему аватаров в Yask: пользователь может загрузить,
заменить и удалить изображение профиля. Исходные файлы хранятся в приватном
S3-совместимом object storage, а приложение использует только обработанный
вариант изображения.

Функция должна работать с текущими профилями, лентой, комментариями и публичными
профилями, не раскрывая storage credentials и внутренние object keys клиенту.

## Цели

- Дать пользователю понятный flow загрузки, замены и удаления аватара.
- Хранить изображения в MinIO на staging и в S3-совместимом storage на production.
- Принимать только безопасные и поддерживаемые форматы.
- Нормализовать размер, ориентацию и метаданные изображения на backend.
- Показывать аватар одинаково во всех местах приложения.
- Сохранить fallback с первой буквой имени, если аватар отсутствует или недоступен.

## Не входит в задачу

- Обложки профиля.
- Галерея нескольких изображений.
- Редактор стикеров, рамок и фильтров.
- Импорт аватара из социальных сетей.
- Публичный доступ к MinIO/S3 console или bucket.
- Хранение оригинального пользовательского файла после обработки.

## Пользовательские истории

- Как пользователь, я могу выбрать изображение из галереи телефона и установить его аватаром.
- Как пользователь, я могу заменить текущий аватар новым изображением.
- Как пользователь, я могу удалить аватар и вернуться к буквенному fallback.
- Как пользователь, я вижу свой аватар в профиле и после перезапуска приложения.
- Как пользователь, я вижу аватары авторов в ленте и комментариях.
- Как публичный пользователь, я вижу аватар другого активного пользователя.
- Как пользователь, я получаю понятную ошибку, если файл слишком большой, повреждён или имеет неподдерживаемый тип.

## Функциональные требования

### Backend и API

1. API должно поддерживать загрузку аватара авторизованным пользователем.
2. API должно поддерживать замену аватара повторной загрузкой нового файла.
3. API должно поддерживать удаление аватара через отдельный endpoint.
4. Неавторизованный пользователь не может загружать, заменять или удалять аватар.
5. Backend должен принимать `multipart/form-data` с одним полем `avatar`.
6. Максимальный размер входного файла: 5 MB. Лимит должен проверяться до полной записи файла в память.
7. Разрешённые форматы входного файла: JPEG, PNG и WebP.
8. MIME type из заголовка multipart нельзя считать единственным источником истины: backend должен проверить фактическую сигнатуру файла.
9. SVG, GIF, анимированные изображения, документы и файлы с неизвестным форматом должны отклоняться.
10. После успешной обработки backend должен сохранять только нормализованный файл в storage.
11. Обработанный аватар должен быть квадратным WebP размером 512x512 px или меньше, с сохранением пропорций и crop по центру.
12. Backend должен корректно применять EXIF orientation и удалять EXIF/прочие пользовательские metadata перед сохранением.
13. Object key должен быть непредсказуемым и не должен строиться из имени загруженного файла. Рекомендуемый формат: `avatars/{userId}/{uuid}.webp`.
14. При замене старый object должен удаляться после успешной записи нового и обновления профиля.
15. При удалении объект должен удаляться из storage, а `profiles.avatar_object_key` должен становиться `NULL`.
16. Операции должны быть идемпотентными настолько, чтобы повторное удаление отсутствующего аватара возвращало успешный результат.
17. API не должен возвращать storage credentials или внутренние секреты.

### Предлагаемый API-контракт

#### `POST /profiles/me/avatar`

Авторизация: Bearer token.

Request:

```http
Content-Type: multipart/form-data
```

Поле формы:

```text
avatar=<image file>
```

Успешный ответ `200`:

```json
{
  "user": {
    "id": "uuid",
    "profile": {
      "avatarObjectKey": "avatars/user-id/object-id.webp",
      "avatarUrl": "/media/avatars/user-id"
    }
  }
}
```

#### `DELETE /profiles/me/avatar`

Авторизация: Bearer token.

Успешный ответ `200`:

```json
{
  "user": {
    "id": "uuid",
    "profile": {
      "avatarObjectKey": null,
      "avatarUrl": null
    }
  }
}
```

#### `GET /media/avatars/:userId`

Публичный read-only endpoint для аватаров активных пользователей.

- API получает object key из профиля.
- API читает объект из приватного storage и отдаёт его без раскрытия bucket credentials.
- Для отсутствующего аватара возвращается `404`.
- Ответ должен иметь корректный `Content-Type`, `Cache-Control` и `ETag`.
- Доступ к удалённым, заблокированным и удалённым пользователям должен быть запрещён.

Допускается вариант с короткоживущим presigned URL, если он не приводит к
протухшим URL в мобильном кэше и сохраняет единый контракт клиента.

### Data model

18. Использовать существующее nullable-поле `profiles.avatar_object_key`.
19. В API-моделях добавить `avatarUrl` как nullable производное поле; object key оставить внутренним техническим значением.
20. При отсутствии аватара ответы должны явно возвращать `avatarObjectKey: null` и `avatarUrl: null`.
21. Замена аватара не должна менять `userId`, профиль, username или счётчики.
22. Удаление старых orphan objects должно быть предусмотрено отдельной периодической cleanup-задачей или безопасным job-процессом.

### Flutter

23. В Edit Profile добавить действие выбора изображения.
24. Перед загрузкой показывать локальный preview выбранного файла.
25. Во время загрузки показывать loading state и блокировать повторные действия.
26. После успешной загрузки обновлять avatar state без перезагрузки всей страницы.
27. Добавить действие `Remove photo`, если аватар установлен.
28. После ошибки сохранять текущий аватар и показывать понятное сообщение пользователю.
29. Для выбора файла использовать системный picker с ограничением на изображения.
30. В `UserAvatar` поддержать `avatarUrl`, а не только object key.
31. Во всех местах отображения использовать единый `UserAvatar`:
    - главная лента;
    - карточка опроса;
    - экран комментариев;
    - собственный профиль;
    - публичный профиль;
    - ответы API и локальное состояние после обновления профиля.
32. При `404`, network error или отсутствии URL показывать текущий буквенный fallback.
33. При загрузке изображения использовать memory/disk cache и не создавать новый сетевой запрос при каждом rebuild.

## Безопасность

- Ограничивать размер multipart body на уровне Fastify и reverse proxy.
- Не использовать имя файла, расширение или MIME type клиента для формирования object key.
- Проверять magic bytes и декодирование изображения библиотекой безопасной обработки, например `sharp`.
- Ограничить число пикселей и глубину декодирования, чтобы предотвратить decompression bomb.
- Не сохранять оригиналы и EXIF metadata.
- Не выполнять shell-команды с пользовательским именем файла.
- Не делать MinIO/S3 bucket публичным.
- Логировать только user id, размер, определённый формат и результат операции; не логировать бинарные данные и секреты.
- Rate limit для upload/delete: например, 10 операций на пользователя за 15 минут.

## Ошибки API

Использовать единый формат ошибок:

```json
{
  "error": "avatar_invalid",
  "message": "Please choose a valid image file."
}
```

Минимальный набор кодов:

- `avatar_too_large` — файл больше 5 MB;
- `avatar_unsupported_type` — неподдерживаемый или поддельный тип;
- `avatar_invalid` — повреждённое изображение;
- `avatar_processing_failed` — ошибка безопасной обработки;
- `avatar_storage_unavailable` — storage временно недоступен;
- `avatar_rate_limited` — превышен лимит операций.

## Нефункциональные требования

- Обработка обычного изображения должна занимать менее 2 секунд на staging VPS.
- API не должно удерживать весь файл в памяти одновременно с неограниченным body.
- Сбой storage не должен изменять `avatar_object_key` в базе.
- Сбой удаления старого объекта не должен удалять уже сохраненный новый avatar key; orphan cleanup исправляет остаток позже.
- Все существующие auth/profile/poll/comment ответы должны сохранить совместимость с `null` avatar.

## Приёмочные критерии

1. Пользователь загружает JPEG/PNG/WebP до 5 MB и видит обновлённый аватар.
2. Файл больше 5 MB получает `400` с `avatar_too_large`.
3. Переименованный `.exe`, SVG и повреждённый файл получают `400` и не попадают в storage.
4. Изображение с EXIF orientation отображается правильно и сохраняется без EXIF.
5. Большое изображение уменьшается до заданного размера и не ломает API.
6. Повторная загрузка заменяет аватар, а старый объект удаляется или попадает в cleanup queue.
7. Удаление аватара возвращает `null`, а UI показывает буквенный fallback.
8. Аватар виден в ленте, комментариях, собственном и публичном профиле.
9. После перезапуска приложения аватар остаётся доступным.
10. Ошибка сети/storage не стирает текущий аватар локально.
11. Backend и Flutter тесты покрывают success, validation, replacement, deletion, fallback и storage failure.

## Открытые решения

- Использовать proxy endpoint `/media/avatars/:userId` или presigned GET URLs.
- Нужна ли минимальная сторона изображения, например 64 px.
- Нужно ли поддерживать HEIC/HEIF на iOS и каким конвертером.
- Хранить ли старые object keys в cleanup queue или запускать периодическое сканирование bucket.
- Должна ли загрузка быть доступна только авторизованным пользователям со статусом `active`.
