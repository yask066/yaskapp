# Тестовое окружение и выпуск через Merge

Дата: 2026-11-15. Статус: проект для согласования, реализация не начата.

## Задача и решения пользователя

Пользователь хочет собирать обновления в отдельной тестовой ветке, проверять
их вместе и выпускать в основную версию одним действием. `yaskapp.org`
используется как основное приложение с рабочими данными. Пользователь выбрал
выпуск через Merge в GitHub.

Результат: изменения из рабочих веток попадают в `staging`, автоматически
проверяются и разворачиваются на тестовом сайте. GitHub подготавливает PR
`staging → main`. После ручной проверки пользователь нажимает Merge;
автоматизация обновляет основной сайт и сообщает фактический результат.

## Рассмотренные подходы

1. Автоматически подготовленный релизный PR и выпуск после Merge. Выбран
   пользователем: виден состав обновлений, проверки и история, дополнительная
   панель выпуска не нужна.
2. Ручной workflow Release, самостоятельно объединяющий ветки и выпускающий
   приложение. Возможен, но требует дополнительных полномочий и логики.
3. Кнопка в панели приложения. Не выбрана: добавляет интерфейс и отдельную
   авторизацию для операции, уже доступной в GitHub.

## Что известно из репозитория

- Текущая локальная `main`: `7fdd05d`; перед реализацией проверить актуальную
  удалённую ветку. Старая `develop` существенно отстаёт и не является базой.
- `.github/workflows/ci.yml` проверяет API и web на push в main/master и PR.
  Развёртывание и Flutter-проверки в этом workflow отсутствуют.
- `infra/docker/docker-compose.staging.yml` содержит API, PostgreSQL, Redis,
  MinIO, web, модерацию, workers и Caddy, публикующий порты 80/443.
- Compose project, образы и backup имеют имена с `staging`; инструкция backup
  указывает `/opt/yaskapp` и project `yaskapp-staging`.
- Flutter уже поддерживает отдельные адреса HTTP API и WebSocket при сборке.
- Флаги функций web задаются при сборке: изменение runtime env их не меняет.

Фактическое состояние VPS, DNS, тариф/видимость GitHub, правила веток,
доступные ресурсы и полномочия ещё не проверены. Наличие конфигурации backup
в Git не подтверждает успешность резервных копий на сервере.

## Окружения

Предлагаемые исполнителем значения:

| Назначение | Основное | Тестовое |
| --- | --- | --- |
| Ветка | main | staging, созданная от актуальной main |
| Web | yaskapp.org | test.yaskapp.org |
| API | api.yaskapp.org | api-test.yaskapp.org |
| Модерация | Существующий адрес | moderation-test.yaskapp.org |
| Данные | Существующие рабочие | Новые тестовые аккаунты и данные |

Предпочтение исполнителя — разместить тестовую копию на имеющемся VPS, если
проверка ресурсов это позволяет. Покупка сервера не входит в автоматическое
исполнение. При нехватке ресурсов запросить решение по размещению.

Рабочие Compose project, тома, пути секретов и backup сохранить независимо
от исторического слова staging. Не переименовывать рабочие тома и не запускать
новое окружение с тем же project name. Тестовой копии дать собственные
project, сеть, тома PostgreSQL/Redis/MinIO, env и JWT/cursor секреты.
Рабочие данные и push-токены в тестовое окружение не копировать.

На одном VPS только один внешний proxy занимает 80/443. Добавить в текущий
Caddy отдельные тестовые host-маршруты. Тестовые backend endpoints публиковать
только на loopback и обеспечить проверенный путь к ним из контейнера Caddy;
либо использовать отдельную ingress-сеть для proxy и тестовых HTTP-сервисов.
Выбор механизма оставлен исполнителю после проверки сервера. Не подключать
рабочие API/workers к тестовым БД или тестовые API к рабочим хранилищам.

Тестовые push по умолчанию отключены; отдельный тестовый Firebase-проект
подключается при наличии реквизитов. Это ограничение отмечается в результатах
приёмки. Тестовая панель модерации получает отдельные тестовые учётные записи.

## Ветки, проверки и ручная приёмка

Обычные задачи выполняются в `codex/...` и объединяются через PR в `staging`.
`main` получает релизы через PR из `staging`. Требовать проверки и запретить
обычный прямой push/force push в main, включая повседневный обход администратором.
Проверить поддержку правил тарифом до объявления настройки завершённой.
Не требовать второго человека для согласования: ручное действие владельца — Merge.

Для долгоживущей staging использовать merge commit, не squash/rebase при выпуске.
После релиза main возвращается в staging обычным merge; конфликт не исправляется
автоматическим выбором одной стороны. Срочный hotfix должен пройти проверки
и отдельное описание выпуска, затем вернуться в staging. Автоматический стандартный
выпуск первой версии поддерживает только путь staging → main.

Сохранить существующие API/web проверки, проверить, что зависимости CI реально
поднимаются, добавить Flutter analyze/test и Android debug build. Обязательные
интеграционные проверки используют временные базы, а не БД тестового сайта.
Пропущенные обязательные suites нельзя выдавать за успешную проверку.

После успешных CI, сборки и развёртывания staging выполнить readiness и
автоматизированные smoke-проверки. Создать/обновить один релизный PR, указав:
SHA исходников, ссылки на staging и проверки, перечень изменений и миграций,
идентификаторы образов и ограничения ручной приёмки.

PR автоматически обновляется вместе со staging. Каждый новый commit требует
новых проверок и повторной ручной приёмки изменившейся версии; прежняя проверка
не распространяется на новые изменения. Владелец сверяет SHA в PR и отметке
развёртывания перед Merge. Во время окончательной ручной приёмки не добавлять
новые изменения в staging. При добавлении повторить приёмку актуального SHA.
Auto-merge не включать: успешный CI не заменяет ручное решение о выпуске.

Required checks привязаны к актуальному SHA PR; readiness staging также
должен быть подтверждён для этого SHA. Если main изменился, обновить staging
и повторить проверки. Ошибка CI/deploy/smoke блокирует выпуск.

## Сборки и выпуск

Собирать API, web и модерацию в CI один раз для конкретного SHA. Хранить образы
в GHCR и манифест: source SHA/tree, digest каждого образа, параметры сборки,
набор миграций и результаты staging. Не использовать изменяемый тег latest
как идентификатор выпуска. Настройки окружения передавать при запуске; web
использует относительный API URL. Флаги функций должны совпадать между
проверяемой и выпускаемой web-сборкой.

Выпуск запускается после ручного Merge релизного PR в main. Проверить источник
PR, CI, staging evidence для точного head SHA и совпадение дерева полученного
merge commit с проверенными исходниками. Любое несоответствие останавливает
развёртывание. Продвигать те же digest образов; не пересобирать приложение
из текущего состояния ветки. Конфигурацию deploy брать из проверенного commit.

Порядок: preflight и фиксация текущей версии → backup → миграции → переключение
сервисов → readiness и smoke → запись успешного релиза. Основная база сохраняется;
миграции применяются к ней отдельно от тестовой. Все API и workers получают
согласованную версию. Краткая пауза обслуживания допустима как предложение
исполнителя: существующий согласованный backup приостанавливает writers.
Гарантия zero-downtime не входит в эту схему.

Merge обновляет Git сразу; успешный выпуск на сервер — отдельный результат.
Если deploy не удался, main может быть впереди фактически работающего приложения.
Показывать ошибку, сохранять фактический SHA/digest и возможность повторить
именно этот выпуск. Не объявлять Merge доказательством успешного deploy.

Развёртывания одного окружения выполняются последовательно, без отмены
активного процесса посреди миграции. На сервере применять блокировку,
совместимую с существующим backup. Исключить выпуск устаревшей версии после
более новой и не рассчитывать, что concurrency GitHub сохраняет каждый
промежуточный запуск. Удалённая операция должна завершаться безопасно и оставлять
проверяемый статус при обрыве SSH или потере runner.

## Доступы и GitHub

Разделить staging/production секреты, ограничить SSH deploy-пользователя
задачами нужного окружения и закрепить проверенный SSH host key. В PR из
недоверенных веток не выдавать deploy-секреты и не выполнять их код через
привилегированный pull_request_target. GHCR credentials на сервере — read-only.

Автоматическое создание PR должно запускать CI без дополнительного ручного
подтверждения каждого workflow. Предложение исполнителя — GitHub App,
установленная только на этот репозиторий, с минимальными полномочиями для
PR и синхронизации веток, без обхода защиты main. Если её нельзя настроить,
выбор альтернативных реквизитов согласовать при подключении доступа.
Штатный GITHUB_TOKEN может потребовать отдельного Approve workflows to run
для автоматически созданного PR; не обещать с ним единственное ручное действие.

GitHub environments использовать при доступности; дополнительные required
reviewers production не включать, чтобы Merge оставался действием выпуска.
При недоступности защиты ветки или ограничения секретов сообщить ограничение
и выбрать поддерживаемую конфигурацию до включения production automation.

## Откат и миграции

Хранить предыдущий манифест и образы. Автоматический возврат приложения
допустим только при доказанной совместимости применённых миграций с предыдущей
версией. Базовый стандарт — расширяющие обратно совместимые миграции; удаление
столбцов и несовместимые изменения требуют отдельного этапа выпуска.

При ошибке миграции не запускать новую версию; выяснить, какие изменения уже
применены, прежде чем возвращать writers. Не выполнять автоматически down
миграции или восстановление всей рабочей БД из backup. При невозможности
безопасного возврата сохранять режим обслуживания и явный failed-статус.
Восстановление данных — отдельная операция с учётом новых пользовательских записей.

## Первичное подключение

1. Проверить VPS, реально запущенные проекты/тома, версии приложения, место,
   успешный backup/restore и существующие DNS/GitHub настройки без изменений.
2. Подготовить workflow и deploy tooling с production deploy выключенным до
   завершения первичной настройки; слияние самого tooling не выпускает код.
3. Настроить отдельный тестовый стек, DNS, credentials и ingress; проверить
   сохранность основного сайта и изоляцию данных.
4. Проверить полный цикл на тестовом окружении, включая отказ и возврат версии.
5. Настроить защиту веток и доступы; зарегистрировать текущую рабочую версию
   и предыдущие образы. Только затем включить обычный выпуск через Merge.

Точные hostnames сервера, пути, ресурсы, способ SSH-доступа, DNS-провайдер,
GitHub тариф и существующие разрешения устанавливаются при инвентаризации.
Если доступа нет, запросить подключение; секреты не просить вставлять в чат.
До подключения можно реализовать и проверить конфигурацию локально, но нельзя
заявить, что удалённая схема работает.

## Объём и критерии готовности

Входит: web, API, модерация, серверные workers, проверки Flutter и отдельная
Android test-сборка с тестовыми API/WebSocket. Предложение исполнителя — отдельный
applicationId и заметное имя тестовой сборки для установки рядом с основной.
Публикация в магазинах, iOS signing и отдельный Firebase-проект не входят
в первый этап; это не означает автоматическое обновление установленных клиентов.

Готовность подтверждается следующими проверками:

- Тестовая регистрация/запись/загрузка не меняет рабочие БД и файлы.
- Push в staging проходит CI, обновляет только тестовый сайт и подготавливает PR.
- Новый SHA не может использовать успешную проверку предыдущего SHA.
- Ошибки CI/staging/migration останавливают дальнейшие действия.
- Ручной Merge выпускает проверенные digest, выполняет smoke и записывает версию.
- Повторный запуск, гонка двух deploy, потеря SSH и отказ readiness обработаны.
- Проверен возврат предыдущих образов с совместимой схемой без восстановления БД.
- Документация описывает обычную разработку, ручную приёмку, выпуск и восстановление.

Существующие ограничения приёмки в docs/staging-smoke-test.md сохраняются;
новый workflow сам по себе не разрешает включение непроверенных функций.
