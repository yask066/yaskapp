# Регулярные резервные копии staging

Цель: ежедневно сохранять согласованное состояние PostgreSQL и медиа MinIO и проверить настоящее восстановление отдельно от действующего приложения.

## Исходные условия

- Стек находится на VPS в `/opt/yaskapp`. Проект Docker Compose называется `yaskapp-staging`.
- Внешнего хранилища сейчас нет. Пользователь разрешил короткую ночную остановку API и workers.
- Существующий скрипт сохраняет только PostgreSQL и требует отдельного смонтированного хранилища; полноценного регулярного backup с медиа не подтверждено.
- Инструменты чата не могут войти по SSH. Установочные и проверочные команды выполняются через открытую SSH-консоль пользователя, с проверкой их вывода.

## Подходы

Доступный сейчас вариант — зашифрованный локальный restic-репозиторий на VPS. Вариант с отдельным сервером/SFTP/S3 предпочтителен для потери VPS, но для него пока нет хранилища и реквизитов; его подключение остаётся отдельным шагом. Вторую директорию на том же диске нельзя представлять как независимую копию.

## Предлагаемая настройка

- Ежедневный systemd timer в 04:00 `Europe/Minsk`, после времени очистки аватаров, указанного в репозитории (03:30). Retention — 30 дней; старые снимки удаляются только после успешной новой копии.
- Шифрованный локальный restic-репозиторий; ключ/пароль находится в root-only файле вне Git и не печатается в логах. Пользователю требуется сохранить пароль отдельно от VPS.
- В копию входят PostgreSQL custom dump, холодный снимок всего тома MinIO (медиа и метаданные), рабочие env/Compose/Caddy/Firebase-файлы для восстановления, манифест с версиями/идентификаторами образов. Пароль самого restic-репозитория не включается в snapshot.
- Перед остановкой — проверка свободного места, доступности инструментов, работающих контейнеров и путей; отказ при нехватке места или небезопасной конфигурации. Фактический объём данных определяется установочным preflight, а не предполагается по ответу «всё норм».
- На время согласованного снимка останавливаются API, изменяющие данные workers/cleanup и MinIO; PostgreSQL остаётся запущенным для pg_dump. Возобновляются только сервисы, которые работали до backup. Возврат сервисов предусмотрен также при ошибке/остановке задания; параллельные backup/drill блокируются общей блокировкой.
- Уведомление об ошибке — ненулевой статус systemd и локальный статус последнего успешного backup; внешний канал оповещений пока не предоставлен.

## Проверка восстановления

- Первый backup проверяется сразу; затем проверка по отдельному еженедельному systemd timer.
- Выполняется чтение/проверка данных репозитория и настоящее извлечение выбранного snapshot в отдельную root-only директорию.
- PostgreSQL восстанавливается в отдельном временном контейнере/томе; MinIO — в отдельном временном контейнере/томе того же образа. Общая сеть изолирована, внешние порты не публикуются; рабочие тома не используются как цель.
- Проверяются восстановление схемы и данных БД, соответствие сохранённым контрольным данным и чтение медиа через S3; после проверки временные ресурсы удаляются только по собственным уникальным именам/меткам.
- Действующий API и workers не подключаются к восстановленной БД; push из drill не отправляется. Тест не переключает трафик и не воскрешает удалённые учётные записи в рабочем приложении.

## Критерии завершения

Реальный backup на VPS создан; восстановление БД и медиа прошло; сервисы после операции работают; ежедневный и еженедельный timers включены и показывают следующие запуски; локальный пароль защищён; ограничения локальной единственной копии явно записаны. Защита от потери VPS без внешнего репозитория не объявляется выполненной.
