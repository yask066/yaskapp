# PRD: Страна в регистрации и профиле

## Краткое описание

В Yask нужно добавить выбор страны при регистрации пользователя и сохранять
страну в профиле. Пользователь должен выбирать страну из выпадающего списка,
а не вводить произвольный текст.

Изменение затрагивает backend, базу данных, Flutter-регистрацию, просмотр и
редактирование профиля, миграцию уже существующих пользователей и тесты.

Для обратной совместимости страна у существующих пользователей сначала будет
`null`. Новые регистрации должны указывать страну. Старым пользователям нужно
показать предложение заполнить страну при следующем удобном входе в профиль,
но не блокировать им авторизацию и использование приложения.

## Цели

- Добавить обязательный выбор страны в новый регистрационный поток.
- Хранить страну в нормализованном виде как ISO 3166-1 alpha-2 код.
- Показывать название страны пользователю, но передавать и хранить код.
- Добавить редактирование страны в профиле.
- Безопасно мигрировать существующие профили без выдумывания данных.
- Сохранить совместимость текущих auth/profile API и сессий.
- Не принимать свободный текст и неизвестные коды стран.

## Не входит в задачу

- Определение страны по IP, GPS или SIM-карте.
- Автоматическое подтверждение места проживания.
- Геолокация, карта и отображение точного города.
- Фильтрация ленты по странам.
- Перевод всех названий стран на отдельный серверный сервис.
- Удаление существующего поля `profiles.location` в рамках этой задачи.
- Обязательное заполнение страны для уже зарегистрированных пользователей.

## Пользовательские истории

- Как новый пользователь, я могу выбрать страну из списка при регистрации.
- Как пользователь, я вижу выбранную страну в своем профиле.
- Как пользователь, я могу изменить страну в настройках профиля.
- Как пользователь старого аккаунта, я могу продолжать пользоваться приложением,
  даже если страна еще не заполнена.
- Как пользователь, я не могу отправить произвольный текст вместо страны.
- Как оператор, я могу выполнить миграцию без сброса существующих профилей.

## Функциональные требования

### Регистрация

1. Форма регистрации должна содержать поле `Country` между основными личными
   данными и кнопкой отправки формы.
2. Поле должно быть dropdown/select с поиском по названию страны.
3. Поле не должно быть свободным текстовым input.
4. Для новой регистрации выбор страны обязателен.
5. До выбора страны кнопка регистрации должна быть недоступна либо запрос
   должен получить понятную ошибку валидации.
6. После выбора на экране отображается локализованное название, а в API
   отправляется ISO alpha-2 код, например `BY`.
7. После успешной регистрации страна должна быть доступна в returned `user`
   и в `/auth/me`.
8. При ошибке сеть/сервер форма не должна терять выбранную страну.

### Профиль

9. Ответы `/auth/me`, `/profiles/me` и публичного профиля должны включать
   `profile.countryCode`.
10. `countryCode` должен быть `string` или `null` для legacy-пользователя.
11. В Edit profile должен быть такой же dropdown со списком стран.
12. Редактирование профиля должно позволять выбрать новую страну.
13. Для legacy-профиля dropdown должен показывать состояние `Not selected`.
14. Обновление профиля должно принимать только разрешенный ISO alpha-2 код.
15. Backend должен поддерживать очистку страны через `null` только для
   legacy-совместимости, если это разрешено продуктовой политикой. В UI
   рекомендуется не показывать очистку для новых профилей.
16. Публичный профиль должен показывать страну только как название, без
   внутренней информации о миграции или статусе заполнения.

### Справочник стран

17. Источником идентификатора страны является ISO 3166-1 alpha-2.
18. Список должен содержать уникальные двухбуквенные uppercase-коды.
19. В списке не должно быть дублей, пустых значений и произвольных
   пользовательских вариантов.
20. Список стран должен быть версионируемым статическим ресурсом приложения
   или backend-каталога. В первой версии рекомендуется хранить общий JSON
   каталог в репозитории, чтобы не зависеть от внешнего API при регистрации.
21. Страна по умолчанию не должна выбираться автоматически без явного действия
   пользователя. Допустимо предварительно показать `Belarus (BY)` только как
   подсказку, но значение должно считаться выбранным лишь после подтверждения.

## Предлагаемый API-контракт

### POST `/auth/register`

Новый обязательный параметр:

```json
{
  "email": "user@example.com",
  "username": "user_123",
  "password": "strong-password",
  "displayName": "User",
  "countryCode": "BY"
}
```

Ошибка для отсутствующего или неизвестного значения:

```json
{
  "error": "validation_error",
  "message": "Request body is invalid.",
  "details": {
    "countryCode": ["Select a valid country."]
  }
}
```

### GET `/auth/me`, GET `/profiles/me`, GET `/users/:userId`

Добавить поле:

```json
{
  "profile": {
    "countryCode": "BY"
  }
}
```

Для старого пользователя:

```json
{
  "profile": {
    "countryCode": null
  }
}
```

### PATCH `/profiles/me`

```json
{
  "countryCode": "PL"
}
```

Для очистки legacy-значения, если такая возможность оставлена:

```json
{
  "countryCode": null
}
```

Неизвестные поля должны по-прежнему отклоняться через strict schema.

## Модель данных и миграция

### Изменение схемы

Добавить в `profiles`:

```sql
country_code CHAR(2) NULL
```

Добавить ограничение:

```sql
CHECK (
  country_code IS NULL
  OR country_code ~ '^[A-Z]{2}$'
)
```

На первом этапе отдельный индекс не нужен: страна не участвует в текущих
поисковых и feed-запросах.

### Миграция существующих пользователей

1. Создать новую SQL-миграцию, которая добавляет nullable-колонку и constraint.
2. Не использовать `profiles.location` для автоматического заполнения:
   свободный текст нельзя надежно преобразовать в страну.
3. Оставить `country_code = NULL` у существующих пользователей.
4. Проверить количество профилей до и после миграции.
5. Запустить миграцию на staging и выполнить smoke-проверку регистрации,
   `/auth/me`, редактирования профиля и старого логина.
6. После проверки применить миграцию на production без удаления volumes и
   без пересоздания базы.
7. В будущем можно добавить мягкий prompt для заполнения страны, но не
   блокировать старые аккаунты.

### Совместимость

- JWT не меняется.
- Существующие refresh/persistent login механизмы не меняются.
- Ответы получают только новое поле, старые поля не переименовываются.
- Backend на переходный период должен корректно читать `NULL`.
- Rollback должен удалять constraint и колонку только до появления данных,
  либо выполняться отдельной процедурой после резервной копии.

## Валидация

### Backend

- `countryCode` для регистрации: обязательная строка длиной 2,
  нормализация в uppercase, проверка по allowlist.
- `countryCode` для PATCH: строка из allowlist или `null` по принятой политике.
- Проверять allowlist на backend, даже если Flutter использует тот же каталог.
- Не доверять названию страны, присланному клиентом.
- Возвращать HTTP 400 и единый `validation_error` для неизвестного кода.

### Flutter

- Использовать модель `CountryOption(code, name)`.
- Хранить в состоянии формы код, а не только отображаемое название.
- Не отправлять запрос до выбора валидной страны.
- Обрабатывать loading/error состояния каталога, если каталог загружается.
- Для статического каталога показывать dropdown сразу, без сетевой зависимости.
- Поддержать корректную прокрутку формы на экранах небольшой высоты.

## UX и доступность

- Поле имеет label `Country` и placeholder `Select your country`.
- Поиск фильтрует список по названию и коду.
- Выбранный пункт имеет визуальное состояние selected.
- Ошибка валидации отображается рядом с полем и не исчезает молча.
- Список доступен с клавиатуры и screen reader.
- Названия стран в первой версии можно показывать на английском с возможностью
  последующего добавления русской локализации.
- Стиль dropdown должен соответствовать текущим auth и profile экранам.

## Безопасность и приватность

- Страна считается обычным профильным атрибутом, но не должна использоваться
  для автоматического вывода точного местоположения.
- Не возвращать email, password hash или внутренние migration details.
- Публичная выдача должна использовать тот же access policy, что и профиль.
- Логи не должны содержать пароль или полный payload регистрации.
- В privacy policy добавить упоминание хранения страны, если это требуется
  действующей политикой продукта и юрисдикцией запуска.

## План реализации

1. Зафиксировать каталог стран и модель `CountryOption`.
2. Добавить миграцию `country_code` в `profiles`.
3. Обновить auth repository/service/routes и регистрацию.
4. Обновить profile repository/service/routes и `/auth/me`.
5. Добавить backend validation и migration checks.
6. Обновить Flutter `AuthUserProfile`, auth API client и persistent session
   parsing.
7. Добавить dropdown в регистрацию.
8. Добавить dropdown в Edit profile.
9. Обновить public profile и отображение страны.
10. Добавить backend integration tests и Flutter widget/client tests.
11. Выполнить staging migration, smoke-test и проверить старые аккаунты.
12. Обновить production через backup, `git pull`, migration и rebuild.

## Тестовые требования

### Backend

- Регистрация с валидным `BY`.
- Регистрация без `countryCode`.
- Регистрация с lowercase-кодом и ожидаемой нормализацией либо отказом по
  выбранной политике.
- Регистрация с неизвестным кодом.
- PATCH профиля с валидной страной.
- PATCH профиля с неизвестным кодом, пустой строкой и `null`.
- `/auth/me` возвращает страну для нового пользователя.
- Старый пользователь с `NULL` успешно логинится и получает `countryCode: null`.
- Публичный профиль не раскрывает лишние auth-поля.
- Миграция идемпотентна и не повреждает существующие профили.

### Flutter

- Парсинг `countryCode` и `null`.
- Регистрация отправляет выбранный код.
- Кнопка регистрации блокируется без выбора страны.
- Dropdown показывает список, поиск и selected state.
- Ошибка регистрации сохраняет выбранную страну.
- Edit profile загружает текущую страну и сохраняет новую.
- Legacy-профиль корректно показывает `Not selected`.
- Маленький экран не обрезает dropdown и кнопку регистрации.

### Ручная проверка

1. Зарегистрировать нового пользователя с `Belarus (BY)`.
2. Перезапустить приложение и проверить persistent login.
3. Открыть профиль и убедиться, что страна сохранена.
4. Изменить страну на другую и проверить `/auth/me`.
5. Войти старым пользователем без страны.
6. Убедиться, что старый пользователь не заблокирован и может заполнить
   страну позднее.
7. Проверить невалидный код через HTTP напрямую.

## Критерии приемки

1. Новая регистрация невозможна без выбора страны.
2. В API и базе хранится ISO alpha-2 код, а не свободный текст.
3. Валидные страны принимаются, неизвестные коды отклоняются на backend.
4. Страна сохраняется после logout/login и доступна в профиле.
5. Пользователь может изменить страну в Edit profile.
6. Все существующие пользователи продолжают входить после миграции.
7. Для старых профилей `countryCode` равен `null`, пока пользователь сам его
   не заполнит.
8. Публичный профиль показывает только разрешенные профильные данные.
9. Миграция выполняется без потери пользователей, профилей и опросов.
10. Backend и Flutter-тесты проходят, а staging smoke-test подтвержден.

## Открытые решения перед реализацией

- Нужны ли русские названия стран уже в первой версии?
- Разрешать ли пользователю очищать страну после выбора?
- Показывать ли страну публично всем пользователям или только владельцу
  профиля?
- Должна ли новая регистрация быть заблокирована при недоступном каталоге,
  если каталог в будущем станет серверным?
- Нужно ли отдельно обновить privacy policy перед production-релизом?
