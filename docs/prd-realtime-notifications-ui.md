# PRD: Realtime-уведомления и Notifications UI

**Статус:** Approved for implementation planning

**Дата:** 2026-09-19

**Платформы:** Flutter, Web
**Связанный foundation:** `docs/prd-notifications.md`

## 1. Резюме

Yaskapp должен предоставлять единый центр in-app уведомлений в Flutter- и
web-клиентах. Новые уведомления и изменения read-state появляются в интерфейсе
в реальном времени, а PostgreSQL остаётся источником истины и восстанавливает
состояние после разрывов соединения.

Задача развивает уже существующий backend inbox, WebSocket hub и базовый
Flutter-экран. Она заменяет локальные и неполные realtime-интеграции единым
app-wide потоком, добавляет production-ready fan-out через Redis и создаёт
полноценный Notifications UI на обеих платформах.

Системные push-уведомления через FCM/APNs не входят в эту задачу. Модель целей и
маршруты должны оставаться совместимыми с будущими push deep links.

## 2. Проблема

Текущая реализация не образует целостный продуктовый сценарий:

- Flutter создаёт realtime-клиент внутри экрана Notifications, поэтому badge и
  другие экраны не имеют общего источника актуального состояния.
- При открытии Flutter inbox все уведомления автоматически помечаются
  прочитанными.
- Нажатие на Flutter-карточку открывает информационный bottom sheet вместо
  связанного опроса, комментария или профиля.
- Текущий `notification.created` не содержит полной модели карточки, поэтому
  realtime-элемент отображается без части данных до следующего HTTP-запроса.
- Web-клиент не имеет Notifications UI и realtime-клиента; ссылки ведут на
  фиктивный query-параметр страницы поиска.
- Серверный realtime hub хранит соединения только в памяти процесса и не
  доставляет события между несколькими API-инстансами.
- Reconnect, heartbeat, backoff и восстановление пропущенных событий не
  определены как единый контракт.

## 3. Цели

1. Дать пользователю единый, понятный и доступный inbox в Flutter и web.
2. Обновлять badge, список и read-state без ручного refresh при активном
   соединении.
3. Синхронизировать состояние между платформами, вкладками и устройствами.
4. Восстанавливать корректное состояние через HTTP после пропуска realtime-
   событий.
5. Обеспечить работу realtime fan-out при нескольких API-инстансах.
6. Реализовать прямую навигацию к опросу, комментарию или профилю.
7. Сохранить обратную совместимость с существующим HTTP inbox и будущими push
   deep links.

## 4. Не входит в задачу

- FCM/APNs и системные push-уведомления.
- Email и SMS.
- Quiet hours и OS-level badge.
- Агрегация нескольких событий в одну карточку.
- Пользовательское удаление или архивирование уведомлений.
- Новые типы уведомлений сверх `poll_vote`, `comment`, `comment_reply`, `like`
  и `follow`.
- Transactional outbox и гарантированная доставка WebSocket-событий.
- Поиск по истории уведомлений.

## 5. Пользователи и основные сценарии

### 5.1 Получение уведомления

Авторизованный пользователь находится на любом экране Flutter или web. После
значимого действия другого пользователя badge обновляется без refresh. Если
inbox открыт, новая карточка появляется сразу либо предлагается через плашку
«Новые уведомления», когда пользователь прокрутил список вниз.

### 5.2 Просмотр inbox

Пользователь открывает Notifications и видит уведомления от новых к старым,
сгруппированные по времени. Сам факт открытия экрана не изменяет read-state.

### 5.3 Открытие уведомления

Нажатие на карточку оптимистично помечает только её прочитанной и открывает
целевой объект. Серверный ответ или последующая reconciliation подтверждает
read-state.

### 5.4 Прочитать всё

Пользователь явно выбирает «Прочитать все». Все активные клиенты получают
обновлённый read-state и устанавливают badge в ноль.

### 5.5 Несколько клиентов

Пользователь держит открытыми Flutter и web. Чтение уведомления в одном клиенте
обновляет второй без ручного refresh.

### 5.6 Восстановление связи

После reconnect или возврата приложения/вкладки в foreground клиент выполняет
HTTP reconciliation. Пропущенные события появляются в inbox, а badge принимает
серверное значение.

### 5.7 Недоступная цель

Если опрос, комментарий или профиль удалён либо недоступен по правилам
видимости, уведомление остаётся в истории. Клиент показывает понятное сообщение
и не открывает пустой или ошибочный экран.

## 6. Продуктовые требования

### 6.1 Общий Notifications UI

Обе платформы должны поддерживать:

- отдельный inbox;
- фильтры «Все» и «Непрочитанные»;
- группы «Сегодня», «Вчера», «Ранее»;
- cursor pagination;
- состояния initial loading, skeleton, empty, error/retry и loading-more;
- визуальное отличие непрочитанной карточки: фон, насыщенность заголовка и
  отдельный индикатор;
- относительное время с доступным полным timestamp;
- явное действие «Прочитать все»;
- переход в настройки in-app уведомлений;
- badge с точным числом от 1 до 99 и значением `99+` выше этого порога.

Во Flutter дополнительно используется pull-to-refresh. В web интерфейс должен
быть адаптивным: центральная колонка на desktop и одноколоночный список на узких
экранах.

### 6.2 Правила прочитанности

- Открытие inbox не меняет read-state.
- Уведомление становится прочитанным только после нажатия на его карточку либо
  явного действия «Прочитать все».
- Нажатие обновляет UI оптимистично.
- Ошибка mutation не удаляет карточку. Клиент восстанавливает серверное
  состояние при reconciliation и показывает ненавязчивую ошибку, если
  пользователь остаётся в текущем контексте.
- Повторный read-запрос безопасен и возвращает актуальное состояние.

### 6.3 Навигация и deep links

| Тип | Цель |
|---|---|
| `poll_vote` | Опрос |
| `comment` | Обсуждение опроса с прокруткой и подсветкой комментария |
| `comment_reply` | Обсуждение опроса с прокруткой и подсветкой ответа |
| `like` с `commentId` | Связанный комментарий |
| `like` без `commentId` | Опрос |
| `follow` | Публичный профиль actor |

Flutter использует внутренний navigator, web — канонические URL. Модель цели не
должна зависеть от способа доставки и впоследствии используется push deep link
без изменения семантики.

### 6.4 Новые события при прокрутке

- Если inbox находится в начале списка, новая карточка вставляется сверху без
  анимации, меняющей текущую позицию неожиданным образом.
- Если пользователь прокрутил список, новые карточки временно накапливаются, а
  над списком появляется плашка с их количеством.
- Нажатие на плашку переносит к началу списка и показывает накопленные
  карточки.
- Повторно полученный `id` не создаёт вторую карточку.

### 6.5 Настройки

В рамках этой задачи Flutter и web дают доступ к существующим настройкам
`inApp` по каждому поддерживаемому типу. Push-настройки не расширяются и не
позиционируются как готовая пользовательская возможность в рамках этого PRD.

## 7. Информационная архитектура клиентов

### 7.1 App-wide notification store

Каждый клиент имеет один notification store на авторизованную сессию. Store:

- загружает начальный unread count;
- хранит нормализованные элементы по `id` и порядок inbox;
- управляет страницами и cursor;
- обрабатывает optimistic read/read-all;
- принимает realtime-события;
- дедуплицирует элементы;
- выполняет reconciliation;
- очищается при logout или смене пользователя.

Экран Notifications и элементы навигации подписываются на этот store. Они не
создают собственные WebSocket-соединения и не поддерживают отдельные копии
unread count.

### 7.2 App-wide realtime client

На одну авторизованную сессию создаётся одно WebSocket-соединение:

- соединение запускается после успешной аутентификации;
- закрывается при logout;
- Flutter авторизуется bearer token существующим способом;
- web использует защищённую cookie-сессию;
- heartbeat выявляет зависшее соединение;
- reconnect использует exponential backoff с jitter;
- параллельные reconnect-попытки запрещены;
- после каждого `connection.ready` запускается reconciliation.

WebSocket-клиент предоставляет типизированный поток событий и не содержит
экранной логики.

### 7.3 Web-маршрут

Добавляется защищённый маршрут `/notifications`. Все существующие ссылки
Notifications в header и sidebar переводятся на него. Фиктивный маршрут
`/search?view=notifications` больше не используется.

## 8. Backend-архитектура

### 8.1 Источник истины

PostgreSQL остаётся durable-источником списка, read-state и unread count.
WebSocket ускоряет отображение изменений, но не заменяет HTTP API.

### 8.2 Создание уведомления

1. Domain action и notification создаются в одной PostgreSQL-транзакции, где
   это уже поддерживается текущей repository boundary.
2. Дедупликационный ключ предотвращает повторную запись.
3. Транзакция фиксируется.
4. После commit backend публикует персональное событие в Redis.
5. Все API-инстансы получают событие, но отправляют его только локальным
   соединениям нужного пользователя.

Сбой между commit и Redis publish не приводит к потере уведомления: запись
остаётся в PostgreSQL и восстанавливается при reconciliation. Guaranteed
realtime delivery для этого окна требует outbox и не входит в текущий scope.

### 8.3 Realtime fan-out

Текущая in-memory карта соединений остаётся локальным транспортным слоем одного
API-инстанса. Redis pub/sub является межинстансовой шиной. Сообщение Redis
содержит recipient ID и версионированное событие; recipient ID не передаётся
клиенту как доверенный параметр.

Read и read-all публикуются тем же способом после успешного изменения в
PostgreSQL, чтобы обновить все устройства пользователя.

## 9. Каноническая модель

```ts
type NotificationType =
  | 'poll_vote'
  | 'comment'
  | 'comment_reply'
  | 'like'
  | 'follow';

type NotificationTargetType = 'poll' | 'comment' | 'profile';

type NotificationItem = {
  id: string;
  type: NotificationType;
  actor: {
    id: string;
    username: string;
    displayName: string;
    avatarUrl: string | null;
  } | null;
  targetType: NotificationTargetType;
  pollId: string | null;
  commentId: string | null;
  payload: Record<string, unknown>;
  readAt: string | null;
  createdAt: string;
  isTargetAvailable: boolean;
};
```

`payload` содержит только заранее разрешённые display-поля. Клиент не получает
email, закрытые профильные данные, moderation reason, storage object keys,
токены либо полный текст приватного контента.

TypeScript-модель и realtime union располагаются в `packages/shared`. Flutter
использует эквивалентную строго типизированную Dart-модель с проверкой
обязательных полей и безопасным игнорированием неизвестных типов.

## 10. HTTP API

Все endpoint’ы требуют авторизованную сессию и работают только с уведомлениями
текущего пользователя.

### 10.1 Список

`GET /notifications?limit=25&cursor=<opaque>&unreadOnly=false`

```json
{
  "items": [],
  "nextCursor": null,
  "unreadCount": 0
}
```

Порядок стабилен: `created_at DESC, id DESC`. Cursor непрозрачен для клиента.
Повторяющиеся элементы между HTTP-страницами и realtime дедуплицируются по
`id`.

### 10.2 Unread count

`GET /notifications/unread-count`

```json
{ "unreadCount": 3 }
```

Endpoint используется для дешёвой инициализации badge без загрузки inbox.

### 10.3 Прочитать одно

`POST /notifications/:id/read`

```json
{
  "notificationId": "uuid",
  "readAt": "2026-09-19T12:00:00.000Z",
  "unreadCount": 2
}
```

Повторный запрос идемпотентен и возвращает исходный `readAt`. Чужой или
несуществующий ID возвращает `404` без раскрытия ownership.

### 10.4 Прочитать всё

`POST /notifications/read-all`

```json
{
  "readAt": "2026-09-19T12:00:00.000Z",
  "updatedCount": 2,
  "unreadCount": 0
}
```

Операция атомарна и идемпотентна. Все затронутые строки получают один серверный
timestamp.

### 10.5 Настройки

Сохраняются существующие endpoint’ы:

- `GET /notification-preferences`;
- `PATCH /notification-preferences`.

Клиенты редактируют только поддерживаемые `inApp`-настройки этого этапа.

## 11. Realtime-контракт

Каждое событие верхнего уровня содержит `version: 1`.

### 11.1 Создано уведомление

```json
{
  "version": 1,
  "type": "notification.created",
  "payload": {
    "notification": {},
    "unreadCount": 4
  }
}
```

`notification` соответствует полной модели `NotificationItem`.

### 11.2 Прочитано одно

```json
{
  "version": 1,
  "type": "notification.read",
  "payload": {
    "notificationId": "uuid",
    "readAt": "2026-09-19T12:00:00.000Z",
    "unreadCount": 3
  }
}
```

### 11.3 Прочитано всё

```json
{
  "version": 1,
  "type": "notifications.read_all",
  "payload": {
    "readAt": "2026-09-19T12:00:00.000Z",
    "unreadCount": 0
  }
}
```

### 11.4 Соединение готово

`connection.ready` означает, что транспорт готов, но не доказывает отсутствие
пропущенных событий. Получив его, клиент запускает HTTP reconciliation.

Неизвестная версия или неизвестный тип события не закрывает соединение. Клиент
игнорирует событие, регистрирует техническую метрику и полагается на HTTP-
сверку.

## 12. Reconciliation

Reconciliation выполняется:

- при старте авторизованной сессии;
- после каждого успешного WebSocket reconnect;
- при возврате Flutter-приложения в foreground;
- при возврате web-документа в `visible` после фонового состояния;
- после неоднозначного результата read/read-all mutation.

Клиент повторно загружает первую страницу inbox и unread count, объединяет
элементы по `id`, заменяет серверные поля `readAt` и `isTargetAvailable` и
сохраняет уже загруженную историю, если она не конфликтует с серверным порядком.
Явный pull-to-refresh выполняет ту же операцию.

## 13. Безопасность и приватность

- Backend определяет recipient только из domain action и авторизованной
  сессии; клиент не передаёт recipient для создания уведомления.
- Все list/read операции проверяют ownership на сервере.
- Redis channel и локальный hub маршрутизируют событие по recipient ID.
- WebSocket handshake для web проверяет разрешённый `Origin` и cookie-сессию.
- Flutter использует действующий bearer token; token не помещается в URL.
- Read endpoints и handshake защищены существующими rate limits с отдельными
  метриками отказов.
- Логи не содержат текст уведомления, содержимое комментария, access token,
  device token или другие приватные данные.
- Block, privacy и visibility rules применяются при создании уведомления и при
  открытии цели.
- Self-notifications и отключённые in-app типы не создаются.

## 14. Доступность

- Все интерактивные элементы доступны с клавиатуры в web.
- Focus state заметен и не зависит только от цвета.
- Карточка имеет понятное screen-reader имя: actor, действие, цель и время.
- Unread-state передаётся семантически, а не только цветом.
- Touch target во Flutter не меньше 44×44 logical pixels.
- Контраст текста, индикаторов и кнопок соответствует WCAG AA.
- Анимации учитывают системную настройку reduced motion.

## 15. Метрики успеха и наблюдаемость

### 15.1 Продуктовые и SLO-метрики

- При стабильном соединении p95 от commit до появления badge и карточки — не
  более 2 секунд в одном регионе.
- После reconnect или foreground reconciliation клиент сходится с backend не
  позднее 5 секунд при доступной сети.
- Повторная доставка одного события создаёт 0 дополнительных карточек.
- Read-state двух активных клиентов сходится не позднее 2 секунд после
  успешного server mutation.
- 100% поддерживаемых типов имеют определённые текст, иконку и deep-link цель.

### 15.2 Технические метрики

- количество активных WebSocket-соединений;
- reconnect attempts и причины disconnect;
- Redis publish/subscribe errors;
- latency `commit → publish → client receive`;
- HTTP reconciliation success/failure и duration;
- unknown realtime version/type;
- read/read-all success, failure и rate-limit responses.

Метрики и логи не включают пользовательский notification payload.

## 16. Тестирование

### 16.1 Backend

- unit-тесты сериализации полной модели и версионированных событий;
- integration-тесты create-after-commit, read, read-all и unread count;
- проверка idempotency и recipient isolation;
- проверка Redis fan-out между двумя API-инстансами;
- reconnect/connection-ready contract tests;
- проверка безопасного payload и недоступной цели;
- проверка cookie/bearer authentication и web Origin policy;
- проверка rate limits и отсутствия публикации до commit.

### 16.2 Flutter

- unit-тесты notification store, merge/dedup и optimistic mutations;
- widget-тесты badge, фильтров, групп, состояний и пагинации;
- lifecycle-тесты одного app-wide соединения, foreground reconciliation и
  logout cleanup;
- integration-тесты всех deep-link переходов;
- тест, подтверждающий, что открытие inbox не изменяет read-state;
- тест накопления новых элементов при прокрутке.

### 16.3 Web

- unit-тесты API decoders, store/query integration и realtime reducer;
- component-тесты route, badge, фильтров, групп и всех UI-состояний;
- тесты reconnect, visibility reconciliation и session cleanup;
- e2e-тесты keyboard navigation и deep links;
- тест замены всех ссылок `/search?view=notifications` на `/notifications`.

### 16.4 Сквозной smoke

Два тестовых пользователя выполняют действия, создающие все пять типов
уведомлений. Получатель одновременно авторизован в Flutter и web. Проверяются
realtime-появление, badge, read одного элемента, read-all, reconnect, пагинация
и недоступная цель.

## 17. Acceptance criteria

1. Flutter и web используют один notification store и одно realtime-соединение
   на авторизованную сессию.
2. Badge обновляется на любом экране и не очищается от простого открытия inbox.
3. Web имеет защищённый `/notifications`; фиктивные ссылки удалены.
4. Inbox обеих платформ поддерживает all/unread, группировку, pagination,
   loading, empty, error/retry и loading-more.
5. `notification.created` передаёт полный безопасный `NotificationItem`.
6. `notification.read` и `notifications.read_all` синхронизируют все активные
   клиенты пользователя.
7. Redis обеспечивает recipient-scoped fan-out между API-инстансами.
8. Старт, reconnect и foreground запускают HTTP reconciliation.

10. Недоступная цель обрабатывается без падения и остаётся в истории.
11. Повторная доставка и повторные mutations идемпотентны.

## 18. Порядок релиза

1. Расширить общие модели и backend HTTP responses без удаления существующих
   полей.
2. Добавить Redis fan-out и версионированные realtime-события.
3. Выпустить web store, realtime client, badge и `/notifications`.
4. Перевести Flutter на app-wide store и realtime client, затем обновить UI и
   навигацию.

игнорируют; backend не удаляет старые поля до завершения миграционного окна.
