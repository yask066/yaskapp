# PRD: Полная пагинация ленты и комментариев

**Продукт:** Yaskapp — Flutter Android и web.<br>
**Дата:** 19 октября 2026 года.<br>
**Статус:** Draft for review. T01 решения приняты 19 октября 2026 года; остальные требования PRD остаются на review. Реализация в рамках подготовки PRD не выполняется.<br>
**Владелец:** Product / Engineering.<br>
**Масштаб:** большой эпик с общим API-контрактом и отдельными этапами backend, Flutter, web и QA.
[Решения T01 по API, snapshots и rollout](superpowers/specs/2026-10-19-feed-comments-pagination-decisions.md).

## 1. Проблема и ожидаемый результат

Пользователь должен дочитывать ленту и обсуждение до фактического конца. Сейчас ограничение первой выборки скрывает часть контента: API возвращает до 20 опросов и до 50 корневых комментариев по умолчанию, а клиенты не запрашивают продолжение. У ответов на комментарии пагинация уже существует, но её необходимо согласовать с новыми правилами списков.

Результат эпика: последовательная загрузка доступного контента без повторов и пропусков на неизменном наборе данных; понятные загрузка, ошибка, повтор и конец списка; сохранение места чтения; корректные действия с опросами и комментариями на любой странице.

Охват включает основную ленту, ленту подписок, корневые комментарии и ответы на Flutter Android и web. Новая персонализация и пагинация профилей не включаются. Порядок roots, cursor policy, popular snapshots и rollout зафиксированы в ADR T01; изменения этих решений требуют review до изменения поведения.

## 2. Основание: что есть в коде

Состояние проверено по текущему checkout на дату документа. Это анализ исходников, а не результат запуска приложения или нагрузочных тестов.

| Область | Текущее поведение | Что требуется |
|---|---|---|
| `GET /polls` | `limit` 1–50, по умолчанию 20; `newest` или `popular`; ответ `{ items }` | Продолжение выборки и явный конец |
| Порядок ленты | `created_at DESC, id DESC`; popular сначала использует `votes_count * 2 + likes_count * 1.5 + comments_count` | Сохранить хронологический порядок; стабилизировать ранжирование на время чтения popular |
| `GET /polls/subscriptions` | Авторизация, опросы авторов из подписок; только ограниченная первая выборка | Независимая пагинация подписок |
| Flutter Feed | `listPolls()` возвращает список, догрузки нет | Модель страницы и контроллер продолжения |
| Web Feed | `useQuery`, одна выборка; вкладки For you и Following вызывают общий `listPolls()` | Пагинация; Following должен использовать `/polls/subscriptions` |
| Корневые комментарии | API сортирует `created_at ASC, id ASC`; клиенты читают до 50, без курсора | Постраничный контракт; явный порядок |
| Создание корневого комментария | Flutter добавляет в конец, web — в начало | Одинаковое согласованное поведение |
| Ответы | API и оба клиента используют `nextCursor`; порядок ASC, размер по умолчанию 20 | Сохранить, проверить гонки, dedup и взаимодействие с корневыми страницами |
| Переход из уведомления | Есть `getComment`; отсутствующий корень добавляется отдельно; поиск далёкого ответа может читать страницы последовательно | Адресно показать цель без чтения всей ветки |
| Состояние опросов и scroll | Есть `PollStateStore` / web `poll-state`, revisions и средства сохранения якоря | Встроить новые страницы в существующие механизмы |
| Shared DTO | `ListPollsResponse` и `ListPollCommentsResponse` содержат только `items`; `PollComment` не отражает все поля ответов | Синхронизировать shared, backend и оба клиента |

## 3. Цели, границы и варианты решения

### Цели

- Дать доступ ко всем страницам основной ленты, подписок и обсуждений.
- Обеспечить одинаковые правила Flutter и web для продолжения, refresh и ошибок.
- Исключить применение устаревших страниц к другому экрану, фильтру или аккаунту.
- Сохранить реакции, удаление, счётчики, навигацию и место чтения при увеличении списка.
- Сделать результат проверяемым через API-, клиентские и сквозные сценарии.

### Не входит

- Новые рекомендации, темы, фильтры и изменение формулы popular.
- Пагинация «Мои опросы», публичного профиля, поиска, уведомлений и админки; их действующие сценарии проверяются на регрессии общих helpers.
- Realtime-доставка новых комментариев, новые уровни вложенности, редактирование комментариев.
- Offline-очередь публикаций, хранение списка и позиции после перезапуска приложения или перезагрузки браузера.
- iOS-приёмка, редизайн карточек, новые анимации и инфраструктура аналитики общего назначения.

### Рассмотренные подходы

| Подход | Плюсы | Ограничения | Решение |
|---|---|---|---|
| Увеличить `limit` или загрузить всё | Малые изменения | Проблема возвращается с ростом данных; большие ответы | Отклонён |
| Номера страниц / OFFSET | Простой переход к номеру | Вставки и удаления сдвигают страницы; глубокие выборки дорожают | Отклонён |
| Cursor по устойчивому порядку; отдельная стабильная выдача popular | Предсказуемое продолжение, подходит текущему UX | Нужны управление сессией списка и решение для изменяемого rank | Рекомендуется |

## 4. Пользовательские сценарии

1. Пользователь листает основную ленту, получает следующие опросы и видит конец только после ответа сервера об отсутствии продолжения.
2. Пользователь переключается в подписки и видит только авторов, на которых подписан; страницы и ошибки общей ленты сюда не попадают.
3. Пользователь ставит лайк на третьей странице, открывает обсуждение и возвращается к той же карточке с актуальной реакцией.
4. Пользователь читает больше 50 корневых комментариев, раскрывает несколько веток и независимо догружает ответы.
5. При ошибке догрузки пользователь продолжает читать загруженное и повторяет только неудавшийся запрос.
6. После создания комментария пользователь сразу видит подтверждённую запись; её последующее получение в странице не создаёт дубликат.
7. Уведомление открывает нужный корень или ответ, даже если он находится далеко за первой страницей.
8. Refresh начинает новую выдачу. Поздний ответ от старой выдачи не изменяет обновлённый список.

## 5. Продуктовые правила

### FR-01. Поверхности и порядок

| Поверхность | Порядок | Размер страницы для новых клиентов | Продолжение |
|---|---|---|---|
| Основная лента / For you | Новые опросы первыми: `createdAt DESC, id DESC` | 20 | Автоматически при приближении к концу + кнопка |
| Подписки / Following | Тот же порядок, только текущие подписки | 20 | Автоматически + кнопка |
| Popular / Trending | Зафиксированный порядок rank, затем `createdAt DESC, id DESC` | 20 | Автоматически + кнопка |
| Корневые комментарии | Новые первыми: `createdAt DESC, id DESC` | 20 | Автоматически + кнопка |
| Ответы конкретного корня | Старые первыми: `createdAt ASC, id ASC` | 20 | Кнопка «Показать ещё ответы» |

Для корневых комментариев это намеренное изменение продукта: новые клиенты явно запрашивают `order=newest`. Запрос без `order` сохраняет старый ASC-порядок и прежний default limit 50. Вкладка For you остаётся хронологической; название не подразумевает создание рекомендательной системы.

У каждого списка свой курсор, ошибка, статус и scroll context. Ответы двух корней не используют общий pending. Курсор корневых комментариев не зависит от того, какие ветки раскрыты.

### FR-02. Догрузка и конец

- Автодогрузка запускается, когда до конца остаётся приблизительно один viewport. Точный порог — настройка реализации, одинаковая по смыслу на двух клиентах.
- Одновременно выполняется не более одного запроса следующей страницы для одной выдачи. Повторные scroll callbacks и нажатия не создают копии запроса.
- Внизу доступна кнопка «Загрузить ещё» для клавиатуры, screen reader и ручного управления. При ошибке автоматика останавливается до ручного Retry.
- Если первая страница не заполняет viewport, разрешено до трёх последовательных автоматических догрузок без нового пользовательского действия; затем остаётся кнопка. Это ограничивает запросы на коротких карточках и скрытом контенте.
- Только `nextCursor: null` означает конец. Размер массива, `commentsCount`, `repliesCount` и число уникальных строк не являются признаком конца.
- Повторный курсор или цикл курсоров останавливает автоматику и показывает восстанавливаемую ошибку; бесконечные запросы запрещены.
- Пустая страница с новым непустым курсором допустима для ranked snapshot после удаления элементов; применяются тот же лимит автоматики и ручное продолжение.
- Конец обозначается нейтральным текстом: «Вы всё посмотрели», «Больше комментариев нет» или «Больше ответов нет». Пустая первая страница показывает отдельный empty state.

### FR-03. Refresh и смена контекста

- Flutter использует pull-to-refresh; web предоставляет явное действие «Обновить». Обновление не подменяется повтором последней страницы.
- Refresh создаёт новую generation выдачи и запрашивает первую страницу без старого cursor. После успеха страницы и cursor заменяются атомарно, раскрытые ветки получают новый контекст и загружаются по необходимости.
- Пока refresh выполняется, старый список остаётся читаемым. При ошибке он сохраняется с локальным сообщением; его старое продолжение снова доступно после завершения refresh.
- Переход к другой сортировке, другому pollId или аккаунту создаёт независимый контекст. Ответ принимается только при совпадении session epoch, list generation и ключа выдачи.
- Возврат к ранее открытой вкладке в той же сессии восстанавливает её данные и якорь в пределах 5-минутного idle cache retention. После истечения cache клиент начинает новую generation с первой страницы и без старого cursor. Logout и смена аккаунта очищают персональные страницы и позиции сразу.
- Background/focus не запускает повторное чтение всех накопленных страниц. Проверка свежести метрик не должна незаметно заменять порядок и курсоры.
- Новые опросы и чужие корневые комментарии появляются при refresh. Самопроизвольной вставки над читаемой областью нет.

### FR-04. Страницы, mutations и актуальность данных

- Объединение по ID: один опрос/комментарий отображается один раз. Страничные cursor metadata не вычисляются из последнего элемента после клиентского merge.
- Вставки, удаления и dedup на клиенте не переписывают серверный cursor. Догрузка идёт от последней подтверждённой серверной страницы.
- Все страницы опросов проходят через существующий механизм revisions и сессионных guards. Поздняя страница не откатывает свежие голоса, лайки, viewer state или `commentsCount`.
- Успешная публикация корневого комментария показывает его в начале через отдельное локальное дополнение к выдаче; при встрече ID в страницах запись объединяется. Страницы и их cursor остаются непрерывной серверной цепочкой.
- Новый собственный ответ виден сразу после подтверждения. Если до него есть ещё незагруженные ответы, он показывается отдельным блоком «Ваш ответ» с обозначением пропуска; его нельзя выдавать за непрерывное продолжение ASC-ветки. Когда серверная цепочка доходит до этого ID, блок объединяется с ней.
- Автопрокрутка к собственной публикации допустима один раз после успешной отправки. Другие обновления не переносят пользователя. Ошибка публикации сохраняет введённый текст и не вызывает автоматическую повторную отправку.
- Удалённые локально записи защищаются от повторного появления из позднего ответа в текущей generation. Удаление корня убирает ветку и её pending-запросы.
- Счётчики берутся из подтверждённого серверного состояния. `commentsCount` учитывает корни и ответы, а не число загруженных корней; `repliesCount` не равно длине локального массива.
- Изменение реакций обновляет карточку без пересортировки popular внутри текущей выдачи.
- Подтверждённый follow/unfollow увеличивает generation только Following. Если список открыт, клиент отменяет старую догрузку и атомарно начинает с первой страницы; если он скрыт, generation инвалидируется и перечитывание происходит при следующем открытии. For you/newest и popular сохраняют страницы и scroll context.

### FR-05. Переход к конкретному комментарию

- Использовать существующий `GET /polls/:pollId/comments/:commentId`; для ответа дополнительно адресно получить корень, если его ещё нет.
- Цель, отсутствующая в непрерывно загруженных страницах, отображается в отдельном блоке контекста «Комментарий по ссылке». Для ответа блок содержит корень и нужный ответ. Наличие блока не меняет основной cursor и не скрывает разрыв в хронологии.
- Открытие цели требует не более двух адресных comment GET сверх обычной загрузки poll и первой страницы комментариев; последовательное чтение всех replies-страниц для поиска цели запрещено.
- При достижении того же ID обычной пагинацией запись объединяется без второй копии и повторного принудительного scroll.
- Явная цель имеет приоритет над сохранённой позицией. После одноразового фокуса ручная прокрутка пользователя имеет приоритет над последующими обновлениями.
- Удалённая/недоступная цель даёт понятное сообщение; доступная часть обсуждения остаётся читаемой. Сетевая ошибка поиска цели предоставляет отдельный Retry.

### FR-06. Прокрутка, производительность и доступность

- Продолжить использование существующих scroll helpers. Якорь хранится по ID элемента и смещению внутри него, с привязкой к пользователю, поверхности, pollId и сортировке.
- Возврат из detail восстанавливает накопленные страницы до восстановления якоря. Пока данные в памяти, повторно скачивать все предшествующие страницы не требуется.
- Догрузка, ошибка footer, реакции и поздняя загрузка изображения не смещают читаемую карточку. Если якорь удалён, используется ближайший сохранившийся сосед.
- Ленты и обсуждения должны создавать элементы лениво. В частности, необходимо оценить замену текущего Flutter comments `SingleChildScrollView` со всеми дочерними элементами на lazy list/slivers.
- Для длинных web-списков выбрать по замерам windowing или иной способ ограничения затрат рендера; он обязан сохранять focus и scroll anchor. Удалять уже загруженные страницы ради ограничения памяти с потерей пути назад нельзя.
- Loading первой страницы отделён от footer loading, refresh и поиска target. Кнопки имеют disabled/pending, ошибки доступны screen reader; догрузка не перехватывает focus.
- Reduced motion соблюдается существующими компонентами; новая пагинация не запускает повторную entry-анимацию ранее загруженных карточек.

## 6. API и совместимость

### API-01. Контракт страницы

Все затронутые list responses используют форму:

```ts
type CursorPage<T> = {
  items: T[];
  nextCursor: string | null;
};
```

`nextCursor` обязателен в новом серверном ответе. Курсор непрозрачен для клиента, передаётся без изменений и URL-encoded. `hasMore`, `totalPages` и обязательный `totalCount` не добавляются.
Для capability detection проверяется наличие `nextCursor`: отсутствующее поле означает legacy-сервер и запрещает append; корректные `string | null` означают поддержку, причём только `null` доказывает конец. Любой другой тип — ошибка контракта.

| Endpoint | Query | Авторизация |
|---|---|---|
| `GET /polls` | `limit`, `sort=newest\|popular`, `cursor?` | Сохранить optional authentication |
| `GET /polls/subscriptions` | `limit`, `cursor?` | Обязательная |
| `GET /polls/:pollId/comments` | `limit`, `order=oldest\|newest`, `cursor?` | Сохранить optional authentication |
| `GET /polls/:pollId/comments/:commentId/replies` | `limit`, `cursor?` | Сохранить optional authentication |

Общие пределы `limit`: целое 1–50. Defaults Feed/subscriptions/replies остаются 20, roots — 50 для совместимости; новые клиенты явно передают 20. Изменение `limit` в продолжении допустимо в этих пределах и не меняет порядок выдачи.

Пример новой цепочки:

```http
GET /polls?sort=newest&limit=20
GET /polls?sort=newest&limit=20&cursor=<opaque>
GET /polls/123/comments?order=newest&limit=20
GET /polls/123/comments?order=newest&limit=20&cursor=<opaque>
```

Примеры путей схематичны: реальные ID проходят существующую UUID-валидацию. Формат элементов Poll/PollComment сохраняет текущие поля, включая viewer state, parentCommentId и repliesCount там, где они уже возвращаются. Shared DTO необходимо привести к фактическим контрактам, включая запрос создания ответа.

### API-02. Cursor и границы выборки

- Для chronological списков — keyset по полной паре `(created_at, id)`, со строгим `<` для DESC и `>` для ASC. Только timestamp недостаточен.
- Cursor строится из точного значения PostgreSQL, включая микросекунды. Сериализация через JS Date с потерей точности для границы запрещена.
- Первая страница фиксирует верхнюю границу хронологической выборки; продолжение сохраняет её, в том числе для ASC-ответов. Новые записи после этой границы доступны в новой выдаче, собственные публикации — через локальный блок.
- Гарантия полного обхода применяется к доступным записям, существующим и неизменным в исходном наборе. Это не долгоживущая SQL-транзакция: удаления и изменения видимости учитываются при каждом чтении, а позже закоммиченные записи могут потребовать refresh.
- `limit + 1` или эквивалентная проверка продолжения выполняется после условий доступности. Удаление граничной записи не ломает cursor: продолжение опирается на значения, а не поиск этой строки.
- Wire format v1 — `c1.<payload-base64url>.<signature-base64url>`; payload — JSON фиксированной схемы, подпись — HMAC-SHA-256. Cursor включает `kind`, sort/order, применимые poll/root IDs и owner scope для персональных выдач. Хронологическая граница и high-watermark содержат timestamp-строки PostgreSQL и ID; для popular используются `snapshotId` и position.
- Ключ `PAGINATION_CURSOR_SECRET` отдельный от `JWT_SECRET`, не менее 32 случайных байт, задаётся в production и общий для всех API replicas. Ротация отзывает старые v1 cursors; клиент начинает новую выдачу. Изменение формата/семантики требует новой версии.
- Cursor валидируется по версии, структуре, длине и контексту. Авторизация проверяется независимо от cursor. Для chronological cursors отдельный TTL не задаётся; popular ограничен сроком snapshot.
- На replies endpoint временно принимается прежний unsigned `{ createdAt, id }` base64url cursor. Он проверяется отдельно, используется только в контексте path `pollId`/`rootId` и сохраняет действующие проверки visibility.

### API-03. Стабильность popular

Popular использует полный серверный snapshot ранжированных ID и порядка на момент первой страницы. PostgreSQL хранит metadata snapshot и отдельные ordered ID с `snapshotId`, `position`, `pollId`. Порядок сохраняет текущую формулу `votes_count * 2 + likes_count * 1.5 + comments_count DESC`, затем `created_at DESC, id DESC`. Продолжение идёт по позиции snapshot; карточки, viewer state и доступность повторно гидратируются на каждой странице. Новый refresh создаёт новый snapshot.

- Срок жизни — 30 минут с создания; чтение не продлевает TTL. SQL-транзакция выполняется в рамках одного HTTP-запроса и не удерживается между запросами.
- Snapshot содержит полный исходный набор доступных ID; фиксированный cap или тихое усечение запрещены. Если построение полного набора не укладывается в staging budget p95 1,5 секунды, запрос/индексы оптимизируются или решение пересматривается до выпуска popular.
- `nextCursor` продвигается по исходным позициям даже при скрытии/удалении ID; недоступный ID не превращается в tombstone с текстом контента.
- На владельца допускается до 3 активных snapshots. При создании четвёртого самый старый вытесняется; его cursor отвечает `410 pagination_expired`. Проверка квоты и вытеснение атомарны.
- Владелец аккаунта определяется user ID, гостя — trusted `request.ip`. В snapshot хранится только HMAC-SHA-256 owner key с domain separation через `PAGINATION_CURSOR_SECRET`; raw IP и user ID не сохраняются. Гости за одним NAT делят квоту. Logout/account switch меняет клиентский session epoch и не переносит cursor между владельцами.
- Cleanup — отдельная одноразовая команда по расписанию каждые 5 минут. Если deployment scheduler отсутствует, добавляется отдельный job container. Клиент сохраняет прочитанное при `410` и предлагает «Обновить ленту»; молча начинать новый snapshot посередине старого нельзя.

### API-04. Ошибки и выпуск

- Ошибки используют `{ error, message, details? }`; `details` остаётся только для validation errors. Неверный, чужой, повреждённый или неподдерживаемый cursor отвечает `400 pagination_cursor_invalid`; просроченный или вытесненный popular snapshot — `410 pagination_expired`.
- Недоступный poll/root/target: `404` по действующим правилам. Подписки без сессии: `401`. Cursor не обходит фильтры visibility, moderation и удаления аккаунта.
- Timeout/5xx сохраняют список; Retry использует тот же последний подтверждённый cursor. Автоповтор публикаций не добавляется. При rate limit клиент учитывает `Retry-After`, если он передан.
- Старый replies cursor принимается 180 дней с production-выпуска Android-клиента, который использует cursor v1. Даты начала и окончания обязательны в release checklist; после окна сервер возвращает `400 pagination_cursor_invalid`.
- Выпуск server-first: additive `nextCursor`, затем web/Android clients. Запросы без cursor и прежние defaults сохраняются. В transition decoder отсутствие `nextCursor` означает неподдерживаемый API, а не конец списка; повторять первую страницу запрещено. Неверный тип поля — ошибка контракта.
- Pagination rollout flags: `VITE_FEED_PAGINATION` для web и `YASKAPP_FEED_PAGINATION` для Flutter (`--dart-define`), оба default `false`. Remote kill switch отсутствует; rollback — новый web/Android build с флагом `false`, первая страница остаётся доступна.
## 7. Модель клиентского состояния

Для каждой выдачи нужны: query/context key, session epoch, generation, server pages и их cursors, упорядоченные уникальные IDs, данные сущностей, локальные дополнения/удаления, initial/refresh/append pending и ошибки, scroll anchor. Это требования к поведению, а не обязательное название класса.

| Состояние | Пользователь видит | Доступное действие |
|---|---|---|
| Initial loading | Skeleton первой страницы | Навигация |
| Empty | Сообщение об отсутствии контента | Refresh |
| Initial error | Ошибка вместо списка | Retry первой страницы |
| Ready | Уже загруженные элементы | Читать, действовать, догружать |
| Appending | Список + footer loader | Читать и действовать, без второго append |
| Append error | Список + локальная ошибка | Retry того же cursor |
| Refreshing | Старый список + индикатор обновления | Читать, без append |
| Refresh error | Старый список + сообщение | Повтор refresh или продолжение старой цепочки |
| Exhausted | Список + сообщение о конце | Refresh |
| Expired popular | Прочитанное + предложение обновить | Создать новую выдачу |

Переход к `InfiniteData` на web требует проверки всех cache updaters: реакции, удаление, создание root/reply, invalidation и session reset. Flutter API должен возвращать объект страницы вместо потери metadata; существующим профильным потребителям нужны адаптеры либо отдельные методы, без неявного изменения их поведения.

## 8. Приёмка

Каждый критерий проверяется на Flutter Android и web, если не указан API-only. Набор тестовых данных воспроизводим, с фиксированными ID и временными метками.

| ID | Сценарий | Условие успеха |
|---|---|---|
| AC-01 | 125 опросов, 125 корней, 65 ответов одного корня; limit 20 | Полный обход каждого списка совпадает с ожидаемым упорядоченным набором; ни повторов, ни пропусков; финальный cursor null |
| AC-02 | 0, 1, 19, 20, 21, 40 элементов | Корректны empty, точная граница и конец; нет лишней бесконечной догрузки |
| AC-03 | Одинаковые created_at и различие в микросекундах | Порядок детерминирован; все ID встречаются ровно один раз |
| AC-04 | Вставки, удаления, скрытие и удаление граничной записи между страницами | Cursor продолжает работать; недоступное не раскрывается; новая выдача включает актуальный доступный набор |
| AC-05 | Scroll storm, двойной tap, медленная сеть | Один append на выдачу; нет повторных параллельных запросов одного cursor |
| AC-06 | Append падает, затем Retry; отдельно — refresh падает | Загруженное и якорь сохранены; append повторяет свой cursor, refresh — первую страницу |
| AC-07 | Refresh обгоняет append; смена вкладки/pollId/аккаунта | Поздний ответ не изменяет новый контекст, viewer state не переносится |
| AC-08 | Реакции и удаление на третьей странице; reordered HTTP/realtime | Свежие значения не откатываются; удалённое не воскресает; все видимые копии poll согласованы |
| AC-09 | Создание root/reply до конца загруженной цепочки | Подтверждённая запись видна, cursor не сдвинут вручную; повторное получение ID не создаёт копию; ASC-разрыв обозначен |
| AC-10 | Одновременная догрузка двух веток | Независимы cursor, pending, ошибки и Retry |
| AC-11 | Target root/reply за десятой страницей; 404 и network error | Цель открывается адресно в бюджете FR-05; нет полного обхода; fallback и отдельный Retry работают |
| AC-12 | Возврат к карточке после detail; media loading; открытая клавиатура | Якорь сохраняется; без пользовательской прокрутки отклонение после стабилизации не более 8 logical px / CSS px; для удалённого якоря выбран сосед |
| AC-13 | Во время popular элементы меняют score и пересекают границу страницы | Порядок текущего snapshot сохраняется; доступный исходный набор обходится без пропусков; refresh отражает новый rank |
| AC-14 | Snapshot истёк или содержит удалённые ID | Управляемый expired state; скрытое не раскрыто; пустые страницы и их продолжение не зацикливаются |
| AC-15 | Guest, Following, чужой cursor и смена подписок | Guest читает публичное; Following требует вход и показывает только подписки; контекст cursor проверяется; смена подписок обновляет выдачу |
| AC-16 | Legacy requests и новые клиенты при выкладке | Сохраняются старые defaults/order и `{ items }` consumers; совместимость replies проверена; неподдерживаемый сервер не вызывает повтор первой страницы |
| AC-17 | Клавиатура, screen reader, увеличенный текст, reduced motion | Продолжение/Retry доступны; focus не теряется; нет повторной entry-анимации старых элементов |
| AC-18 | Сервер повторяет cursor; короткие/пустые страницы | Нет request loop; лимит автоматических догрузок соблюдён; ручное восстановление доступно |

### Обязательные проверки масштаба

- API: fixture минимум 100 000 публичных опросов, 10 000 корней у одного poll и 1 000 ответов у одного корня; замеры первой и глубокой страницы (после 1 000 элементов), отдельно newest/subscriptions/comments/replies/popular.
- Предлагаемый бюджет хронологических read endpoints: p95 серверного ответа не более 500 мс при 20 одновременных читателях на зафиксированной staging-конфигурации. Средний рост времени глубокой страницы относительно первой — не более 2×. Для построения popular snapshot — p95 не более 1,5 с; продолжение — не более 500 мс. Эти значения являются целями приёмки, а не текущими замерами.
- Проверить query plans и индексы для tuple-сортировки, фильтра видимости, parent и подписок; не добавлять полный COUNT на каждый append и N+1 на каждую строку. Изменения индексов сопровождаются миграциями.
- Клиенты: прокрутка минимум 1 000 корней/карточек, несколько раскрытых веток; сравнить с тем же маршрутом на 100 элементах. Цель — менее 5% кадров сверх бюджета 60 Hz на Android profile build и менее 5% кадров дольше 16,7 мс в web performance trace при зафиксированном оборудовании.
- После трёх циклов «открыть → загрузить 10 страниц → выйти» число listeners, активных запросов и retained screen instances возвращается к baseline. Неактивные page caches и anchor context освобождаются не позднее чем через 5 минут; logout/account switch очищает их сразу. Память после освобождения cache не растёт монотонно между циклами; окружение замера фиксируется в отчёте.

## 10. Наблюдаемость и выпуск

- Использовать существующие средства логирования/аналитики. Нужны события page load start/success/failure, retry, refresh и cursor anomaly с surface, sort, номером загруженной страницы, duration, количеством items и error code.
- Не логировать токены авторизации, raw cursor, тексты комментариев и персональные payload. Для диагностики достаточно request ID и технического идентификатора выдачи.
- Контролировать p95 page latency, долю append failures по причинам, cursor loops, дедупликацию и срок/размер хранения popular snapshots. Высокий dedup не считается доказательством корректной серверной пагинации.
- Сначала выкатить совместимый API, затем ограниченно включить web/Android clients флагами `VITE_FEED_PAGINATION` и `YASKAPP_FEED_PAGINATION`, затем расширить охват после smoke и проверки метрик. Флаги build-time, по умолчанию выключены; remote kill switch нет.
- Rollback клиента требует нового web build / Android build с pagination flag `false`; первая страница остаётся доступна. Additive API и нужные старым клиентам cursor decoders сохраняются; удалять новые индексы при rollback без оценки нагрузки не требуется.
- В release record указать commit/build, миграции, платформы/устройства, fixtures, результаты AC и performance, окно совместимости replies и известные ограничения. Непроверенная платформа или популярная лента без стабильного продолжения не отмечаются как готовые.

## 11. Риски и решения на review

| Риск / решение | Предлагаемое правило |
|---|---|
| Изменение порядка корней заметно пользователю | Новые clients явно выбирают newest; legacy ASC сохраняется; решение зафиксировано в ADR T01 |
| Popular snapshot значительно увеличивает backend scope | PostgreSQL snapshots и квоты зафиксированы в ADR T01; P4 подтверждает полный обход и бюджеты, не подменяя их dedup |
| Накопленные страницы ломают cache mutations | Проверить все writers/readers при изменении формы cache, использовать текущие revision guards |
| Большое дерево комментариев ухудшает scroll | Lazy rendering и замеры обязательны до выпуска |
| Target и собственный ответ создают ложную непрерывность | Отдельные контекстные блоки до встречи ID в нормальной цепочке |
| Профиль использует общие API helpers | Сохранить адаптеры и регрессионно проверить; расширение profile pagination вынести отдельно |
| Изменение правил удаления/модерации | Повторно применять доступность на каждой странице и при адресном чтении, независимо от snapshot |

## 12. Definition of Done

Эпик завершён, когда все четыре поверхности из scope работают в Flutter Android и web, включая stable popular; API/shared/client contracts согласованы; выполнена матрица AC-01–18 и проверки масштаба; пройдены целевые backend, Flutter и web tests, typecheck/analyze и сборки затронутых частей; сохранены smoke/performance evidence и release record; rollout и rollback проверены. Известные дефекты целевых сценариев устранены. Статус документа Draft сам по себе не подтверждает ни один из этих пунктов.
