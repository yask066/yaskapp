# API-контракт удаления аккаунта

**Статус:** проект для AD-01; обязателен к проверке вместе с [PRD](prd-account-deletion.md) до начала реализации API.
**Совместимость:** новый контракт; существующие login/logout и Bearer/cookie-сессии продолжают работать по своим контрактам.

## Дополнение: закрытый архив от 2026-10-18

В основной PostgreSQL хранится отдельный снимок идентификаторов/профиля,
недавних IP и материалов связанных нарушений до `deletedAt + 30 дней`.
`completed` подтверждает очистку активных данных; архив остаётся исключением,
раскрытым в web/Flutter подтверждении. Пароли, токены, сессии и медиа исключены.

Все следующие пути требуют superadmin и возвращают `Cache-Control: no-store`:

| Метод и путь | Вход и результат |
| --- | --- |
| `GET /admin/deleted-accounts` | `limit` 1–100, `query` (username/email/UUID), `cursor`; `{ items, nextCursor }` без IP и материалов |
| `GET /admin/deleted-accounts/:userId` | `{ account: { userId, source, deletedAt, expiresAt, profile, ips, evidence } }`; просмотр записывается в аудит |
| `POST /admin/deleted-accounts/:userId/ip-bans` | `{ ip, reason }`; `201 { ban }`. Только IP из действующего архива, без CIDR |
| `GET /admin/ip-bans` | `limit` 1–100, UUID `cursor`; `{ items, nextCursor }` активных блокировок |
| `POST /admin/ip-bans/:banId/revoke` | `{ reason }`; `200 { status: 'revoked' }`, повторная отмена идемпотентна |

На границе `expiresAt` чтение и назначение блокировки возвращают `404`, даже
если worker остановлен. Чужой IP даёт `409 ip_not_in_archive`, текущий IP
оператора — `409 own_ip`, неверная схема — `400`. Причина обязательна,
1–500 символов. Блокировки и их аудит не удаляются вместе с архивом. Входящие
запросы с заблокированного адреса получают `403 ip_blocked`; health и
deletion-only пути исключены.

Этот раздел уточняет исходный draft ниже в части закрытого хранения.

## Принципы

- Для удаления аккаунт всегда определяется на сервере по проверенной сессии либо по паре login/password. Нельзя передать произвольный `userId`.
- Проверка личности выдаёт два случайных разрешения с независимыми сроками и scopes. Они не являются обычной пользовательской сессией.
- Проверка статуса не требует существования строки пользователя: она должна работать после её физического удаления.
- Ошибка до ответа `202` сама по себе не сообщает клиенту, была ли операция принята. Клиент проверяет статус по заранее сохранённому `statusToken`.
- Для cookie-authenticated POST-запросов сохраняется проверка доверенного `Origin`.
- Пароли, специальные токены и их хэши не входят в ответы, URL, аналитические свойства и application logs.

## Общие типы

```ts
type AccountDeletionStatus =
  | 'not_started'
  | 'pending'
  | 'processing'
  | 'retrying'
  | 'completed';

type AccountDeletionStatusResponse = {
  operationId: string;
  status: AccountDeletionStatus;
  acceptedAt: string | null;
  deadlineAt: string | null;
  completedAt: string | null;
};

type AccountDeletionVerificationResponse = {
  operationId: string;
  status: 'not_started';
  deletionToken: string;
  statusToken: string;
  deletionTokenExpiresAt: string;
  statusTokenExpiresAt: string;
};
```

Время — ISO 8601 UTC. Verification готовит операцию и разрешения; она не
блокирует аккаунт и не начинает удаление. Временные значения сроков выше
предварительны, пока не утверждены решения из PRD.

## `POST /auth/account-deletion/verification`

Проверяет пароль и выдаёт ограниченные разрешения.

Для активной сессии клиент передаёт пароль в JSON и существующий Bearer token
или cookie. Login/user ID берутся из серверной сессии; дополнительные
идентификаторы аккаунта в теле запрещены.

```http
POST /auth/account-deletion/verification
Authorization: Bearer <current-session>
Content-Type: application/json
```

```json
{ "password": "current password" }
```

Без действующей сессии клиент передаёт `login` и `password`. Такой способ
позволяет пользователю заблокированного аккаунта подтвердить только удаление;
он не выдаёт обычный access token, cookie или доступ к приложению.

```json
{ "login": "email-or-username", "password": "current password" }
```

Неоднозначные, лишние или одновременно переданные поля отклоняются.
Успех — `200 OK` с `AccountDeletionVerificationResponse`. Новая успешная
проверка отзывает предыдущие неиспользованные verification tokens и заменяет
непринятую подготовленную операцию этого аккаунта.

`deletionToken` действует 10 минут и может быть использован только для
подтверждения удаления связанной операции. `statusToken` действует 48 часов,
разрешает только узнать статус этой операции и не может её принять, отменить
или прочитать пользовательские данные. Сервер хранит хэши случайных токенов;
ответ с токенами показывается только один раз.

Для проверки пароля действует максимум 5 неуспешных попыток за 15 минут на
аккаунт и отдельный лимит по IP. При ограничении `429 Too Many Requests`
возвращается `Retry-After`. Ответ неверного login и парольной комбинации
одинаков по коду и тексту.

## `DELETE /auth/me`

Атомарно принимает одну операцию и немедленно закрывает аккаунт.

```http
DELETE /auth/me
Authorization: Bearer <deletionToken>
Content-Type: application/json
```

```json
{ "confirm": true }
```

`confirm` обязателен и принимает только `true`. `userId`, login, пароль,
параметры очистки и дополнительные поля запрещены. Cookie текущей сессии при
успешном ответе очищается.

При первом принятии сервер в одной транзакции потребляет разрешение,
проверяет защиту последнего действующего superadmin, запрещает новые записи,
фиксирует принятую задачу и время принятия. При успешном commit отвечает
`202 Accepted`:

```json
{
  "operationId": "uuid",
  "status": "pending",
  "acceptedAt": "2026-10-12T10:15:00.000Z",
  "deadlineAt": "2026-10-13T10:15:00.000Z",
  "completedAt": null
}
```

Значение `deadlineAt` отражает действующий срок только после его утверждения.
Повтор корректно авторизованного запроса той же операции возвращает `202` и
ту же квитанцию состояния, не запускает второй worker и не изменяет счётчики
повторно. Для строгого повторения используется consumed token, связанный
с `operationId`; endpoint не интерпретирует новый аккаунт из тела запроса.

Статус операции после acceptance меняется следующим образом:

| Статус | Значение |
| --- | --- |
| `not_started` | Операция подготовлена, но клиент ещё не отправил принятие |
| `pending` | Принята; ожидает обработки worker |
| `processing` | Один или несколько шагов выполняются |
| `retrying` | Шаг временно завершился ошибкой и ожидает повтора |
| `completed` | Обязательные проверки очистки действующих хранилищ прошли |

Подготовленная операция, истёкшая до acceptance, не блокирует аккаунт и может
быть удалена по утверждённому TTL. Уже принятая операция не истекает и не
возвращает аккаунт в active.

## `GET /auth/account-deletion/status`

Возвращает статус операции, связанной с `statusToken`.

```http
GET /auth/account-deletion/status
Authorization: Bearer <statusToken>
```

Успех — `200 OK` с `AccountDeletionStatusResponse`. Для подготовленной
операции возвращаются `status: "not_started"` и `null` во всех временных
полях. Для принятой операции даты указываются согласно реальным timestamps.
`GET` не сообщает существование другого пользователя и остаётся доступным
после отзыва обычной сессии и удаления `users`.

Клиент опрашивает status с интервалом, растущим от 2 секунд до 30 секунд;
после `completed` прекращает опрос и стирает сохранённую квитанцию. `statusToken`
не может получить профиль, email, username, причины/метаданные или прогресс
отдельных шагов очистки.

## Ошибки

Ошибки соответствуют общему API-формату `{ "error": "code", "message": "..." }`.
Клиенты используют `error` для ветвления; `message` предназначен для показа и
не содержит SQL, имён таблиц, storage keys или технических секретов.

| HTTP | `error` | Условие и клиентское поведение |
| --- | --- | --- |
| `400` | `validation_error` | Неверная схема, неизвестные поля или `confirm` не равен `true`; операция не принята |
| `401` | `unauthorized` | Требуется сессия verification либо отсутствует/истёк/отозван deletion/status token; клиент запускает соответствующий flow, а не объявляет удаление успешным |
| `403` | `invalid_credentials` | Неверный пароль; текущая обычная сессия остаётся действительной, форму не закрывать |
| `403` | `last_superadmin` | Нельзя удалить последнего действующего superadmin; операция не принята |
| `403` | `csrf_origin_rejected` | Cookie POST пришёл от недоверенного Origin |
| `409` | `account_deletion_conflict` | Состояние изменилось так, что подготовленную операцию нельзя принять; запросить статус и при необходимости повторить в новом подтверждении |
| `429` | `rate_limited` | Превышен лимит проверки пароля; применять `Retry-After` |
| `503` | `account_deletion_unavailable` | Принятие нельзя надёжно зафиксировать; сохранить квитанцию, проверить status, повторить безопасно |

Внутренняя ошибка после commit не возвращает аккаунт в active. Клиент получает
операцию/статус через status token; состояние `retrying` не представляется как
необратимый отказ. Если acceptance-транзакция откатилась, сервер не должен
отвечать `202`.

## Безопасное хранение клиентской квитанции

После verification мобильный клиент хранит `deletionToken` и `statusToken` в
secure storage, web — только `statusToken` и данные возобновления в
`localStorage` под случайным ключом, не содержащим user ID. В web
`deletionToken` живёт только в памяти страницы и действует 10 минут.
Транспорт передаёт токены в Authorization header, никогда в query/path.
Локальная запись содержит только идентификатор операции для UI, два
разрешения и времена истечения; в ней нет профиля или auth access token.
После `completed` или истечения 48 часов запись удаляется. Недоступность
статуса сохраняет квитанцию и показывает «Проверяем результат».

Web status token — bearer credential в `localStorage`; его объём доступа
ограничен статусом одной операции, но XSS на том же origin всё равно способен
его прочитать. Поэтому CSP и защита web-клиента от XSS обязательны до включения
возобновления после перезапуска. Выбор другого хранилища статуса изменит
требование пережить перезапуск и требует отдельного продуктового решения.

## Текущий web transport

`apps/web/src/api/client.ts` вызывает `onUnauthorized` на любой `401`.
Verification/status/deletion-token запросы используют отдельный transport
без глобального `401 → signOut`, чтобы неверная deletion-only авторизация или
истёкшая квитанция не очищали другую действующую пользовательскую сессию.
Обычные запросы web продолжают использовать HttpOnly cookie и существующий
session provider.

## Предел обещания `completed`

`completed` подтверждает очистку БД, настроенного object storage, управляемых
кэшей, поиска, relationships, notification и moderation data согласно карте
данных. Он не ждёт истечения backup: это срок удаления остаточных backup-копий,
а не часть status операции. Публичный текст может назвать срок backup только
после отдельного решения продукта и доказательства expiry во всех местах
хранения.
